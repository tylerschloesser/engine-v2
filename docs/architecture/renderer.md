# Renderer

A custom WebGPU renderer. Rust in the client worker produces every byte it draws (tile texels, upload records, the sorted DrawList, tables); a thin TypeScript layer on the main thread uploads those bytes and issues the draws inside one `requestAnimationFrame` callback. No WASM runs on the main thread and the renderer holds no game knowledge (user-driven requirement: WebGPU calls from TypeScript on main, frame data from Rust in a worker). Why this split: [0018](../decisions/0018-renderer.md), amended by [0024](../decisions/0024-planning-amendments.md) (§9 `CHUNK_BITS`, §11 slot header) and [0066](../decisions/0066-phase-3-decisions-client-renderer-input.md).

Code:
- Rust: `packages/engine/crates/engine/src/client/` (`drawlist.rs`, `texel.rs`, `upload.rs`, `frame_view.rs`, `terrain_feed.rs`), driven from `game_instance.rs` `frame()`.
- TypeScript: `packages/engine/src/render/` (device, terrain, drawables, art, atlas, upload, viewport, gpu-host, gpu-resources, gpu-timing, `wgsl/*.wgsl`), `frame-loop.ts`, `worker/client-drawlist.ts`, `worker/client-upload.ts`, `support.ts`. `render/client-drawables.ts` `attachClientDrawables` is the public way a game page draws its client's DrawList (builds the drawables renderer over the client's slot, loads the sprite atlas, attaches it to the terrain pass). Public pieces are exported from the `./render` subpath (`src/render.ts`, [0034](../decisions/0034-provisional-render-exports-subpath.md)).
- Game side: `extract` and `tile_visual` in `ClientSide` impls (`games/reference/sim/src/client.rs`), art in `games/reference/assets/` (`tiles.png`/`tiles.json`, `sprites.png`/`sprites.json`).

## Data flow

Per rAF on main, `FrameLoop.tick(tMs)` (`frame-loop.ts`) runs the ordered `FRAME_PHASES`: `acquire`, `camera`, `writeCamera`, `upload`, `render`, `overlay`, `ui`. Before them it applies a pending canvas resize (`ViewportController.applyPending()`). `writeCamera` writes the camera block and bumps `CB_FRAME_REQ`, which wakes the client worker (camera and input: [camera-input-overlay.md](camera-input-overlay.md)). The worker's `frame()` is independent of rAF, so several rAFs can share one produced frame or the reverse.

In the client worker, `GameInstance::frame` (`game_instance.rs`) does: build `FrameView` -> `ClientSide::frame` -> `DrawList::begin_frame(window_origin)` -> `ClientSide::extract(&view, &mut DrawList)` -> `DrawList::sort_into(region, ..)`. Then `worker/client-drawlist.ts` (`createDrawlistPump().publish()`) copies the header plus only the used 64 KiB blocks from the WASM region into the back slot of the `drawList` triple buffer (`sab/triple.ts`) and publishes. A wake that did not run `frame()` publishes nothing.

On main:
- `acquire` phase: `Client.pick.acquire()` calls `DrawListSlot.acquire()` (`render/drawlist-slot.ts`), the only `TripleReader` over the DrawList SAB (a second reader tears the handoff). Camera follow, picking, overlay and render all read that one slot for the tick.
- `upload` phase: `UploadDrain.drain(budget)` (`render/upload.ts`) applies upload-ring records to the `TerrainRenderer` under a byte budget (`DEFAULT_UPLOAD_BUDGET_BYTES` = 64 KiB per frame; a CHUNK charges 4,096, PATCH/INDIR entries 64 each; at least one record when the ring is non-empty).
- `render` phase: `TerrainRenderer.draw(target, { reveal })` (`render/terrain.ts`) encodes one pass. The drawables renderer rides inside it through `terrain.onEncode` (`attachDrawables`): `DrawablesRenderer.acquire()` does the one `queue.writeBuffer(instanceBuf, 0, body, 0, recordCount * 32)`, `encodeInto` issues one instanced `draw(6, n, 0, first)` per non-empty layer. One encoder, one pass, one submit; no depth buffer, bundles or indirect draws.

## The DrawList (`client/drawlist.rs`)

- `Draw` is exactly 32 bytes little-endian, one GPU instance: `pos`, `size` (tiles), `kind_sprite` (bits 12..16 kind, 0..12 sprite id), `layer` (0..8), `flags` (`ANCHOR_CURSOR_TILE`, `SCREEN_PX_STROKE`, `PREDICTED`, `FLIP_X`), `color` (rgba8), `param`, `pick_id` (0 = not pickable). Kinds: sprite, circle, ring, rect, bar, radial, ghost, all drawn by one "uber-quad" pipeline (`wgsl/uberquad.wgsl`). `UBERQUAD_VERTEX_LAYOUT` binds everything except `pick_id`; picking scans the slot on the CPU (`input/pick.ts`).
- The Rust constants (`CAPACITY` 65,536, `DRAW_BYTES`, `HEADER_BYTES` 1,024, `LAYER_COUNT` 8, header offsets) are mirrored by hand in `render/drawables.ts` and `render/drawlist-slot.ts`. Change them together.
- `DrawList::{sprite, circle, ring, rect, bar, radial, ghost}` take an absolute `WorldPos` (Q24.8) and subtract the window origin in integers before the f32 cast, so precision is independent of distance from the world origin. A full list drops the record and bumps `dropped` (header, never grows).
- The window origin is the camera-centre tile snapped down to a multiple of 64 tiles (`snap_window_origin`), so a list does not change with sub-chunk camera motion. The newest camera is applied on main, so a one-frame-old list never mispositions. `ANCHOR_CURSOR_TILE` is resolved in the vertex shader from the live cursor tile (zero ghost latency).
- `sort_into` is a stable counting sort by `layer` (O(n), writes `layer_count[8]` into the header). Header also carries `frame_seq`, `record_count`, `window_origin`, `dropped`, `frame_time_ms`, `follow`, and the 64 overlay anchors (`DrawList::anchor`).
- `FrameView::visible()` is the visible rect plus a 2-tile margin; the capacity assumes `extract` culls to it. `FrameView.zoom` lets a game skip small drawables; the engine applies no entity LOD ([0018](../decisions/0018-renderer.md) §6).
- `hash_region` hashes a DrawList excluding `frame_seq` and `frame_time_ms`; native and `.wasm` must agree (golden `fixtures/drawables`).
- A pending (predicted) tile is not styled by the terrain shader: the tile texel holds only the predicted value, and the game draws a `rect`/`ghost` from `predicted_tiles`; entities carry `PREDICTED` ([0066](../decisions/0066-phase-3-decisions-client-renderer-input.md) §9).

## Terrain (`render/terrain.ts`, `wgsl/terrain.wgsl`)

One full-viewport triangle; the fragment shader goes pixel -> tile -> chunk -> slot -> texel -> art, so cost is per pixel, not per tile, and far zoom needs no LOD (mips converge to the mean colour). Textures:
- Tile page: 1024x1024 `rg16uint`, 1,024 slots of 32x32 chunks (`PAGE_SLOTS`); slot = the chunk's slab index in the client dense cache. Texel = `TileTexel { base, resource }` visual ids, converted by `TileTexel::from_tables` / `ClientSide::tile_visual` (`texel.rs`) on chunk load or tile patch, never per frame. Only `CHUNK_BITS = 5` works in the browser.
- Chunk indirection: 64x64 `r16uint`, toroidal by `chunk & 63`, value = slot or `0xFFFF`. Non-resident chunks draw a neutral colour; a missing neighbour counts as "same as self" for dithering.
- Visual table: uniform of 1,024 x 16 B (`VISUAL_TABLE_BYTES`, the compatibility-mode binding limit). Tile art: `texture_2d_array` of at most 256 images (`MAX_CELLS`) and 1,024 visuals (`MAX_VISUALS`), mips to 1x1.
- Upload records (`client/upload.rs` `Uploader`, `RECORD_BYTES` 4,112 = 16 B header + 4,096 payload): CHUNK (1,024 texels), PATCH (up to 512 entries), INDIR (up to 1,024 entries). A chunk's INDIR is always staged in a later record than its CHUNK, so a slot is never addressed before its texels exist. `worker/client-upload.ts` stages at most `min(free slots, 16)` per wake. `render/upload.ts` writes CHUNK texels straight from the SAB-backed view when `RendererDevice.sabWriteTextureOk` (probed once at startup), else via a preallocated staging array.
- Sampling: variant, flip and brightness jitter come from an integer hash of `(tile_x, tile_y, seed)`; edge dithering is stateless (Bayer on the art-texel grid, `neighbourCutoffPx` turns neighbour reads off below a screen size); magnification uses the `fwidth` "fat pixel" formula, minification trilinear mips; blending is premultiplied alpha; the camera snaps to device pixels at rest.
- Camera-relative: the camera is f64 on main; the frame uniform carries `cam_tile` (i32) and `cam_frac` (f32), the shader computes everything relative to it, so precision is independent of distance (`FrameUniformValues`, `DrawFrameUniformValues`, 48 B each).
- The reveal gate (`draw(target, { reveal: false })` begins the pass, clears, and skips terrain and drawables) is opt-in via `FrameLoopOptions.revealed` / `RealFrameLoopOptions.revealed`; no page or helper in the repo currently passes it (`client.revealed()` exists to wire in), so `reveal` stays `true` and terrain always draws. Wired to `client.revealed`, a join over a slow link would show the clear colour until every visible chunk has arrived ([0066](../decisions/0066-phase-3-decisions-client-renderer-input.md) §10).

## Art contract (`render/art.ts`, `render/atlas.ts`)

The game's own asset script supplies the files; the engine has no art tool. `loadTileArt` reads `tiles.png` (square cells of one size) + `tiles.json` (visual id -> `{first, variants, flags, priority, band}`), validates it (`ManifestError`), uploads with `createImageBitmap` + `copyExternalImageToTexture` (`premultipliedAlpha: true`) into `rgba8unorm` and builds mips (`render/mips.ts` + `wgsl/mips.wgsl`, a blit-based generator used for tile art; the sprite atlas reuses its blit technique for its 2 levels). `loadSpriteAtlas` reads `sprites.png` (at most 4096x4096, extruded padding, exactly 2 mip levels) + `sprites.json` (at most 4,096 sprites: rect, pivot, size in tiles, frame count), validated by `validateSpritesManifest` (`SpriteManifestError`); sprite data goes to two 64x64 `rgba32float` data textures. No compressed formats. Shapes (circle, ring, rect, bar, radial, ghost) need no art. There is no in-canvas text: text is DOM. A game is limited to 256 tile images, 1,024 visuals and 4,096 sprites until an ADR adds a second array or atlas.

## Device, support and lifecycle

- `initDevice` (`render/device.ts`): `requestAdapter({ featureLevel: 'compatibility' })` (an adapter option, not a device one), empty `DEVICE_REQUEST` (`timestamp-query` only with `render.gpuTiming`), `uncapturederror` collected into `errors()`, and two startup probes (`GPUTexture` accepted as attachment `view`; SAB-backed `writeTexture`). Compatibility mode is a design constraint, not a test commitment: instance data in vertex buffers, one view dimension per texture (a texture bound as `2d-array` needs `textureBindingViewDimension: '2d-array'` at creation, [0066](../decisions/0066-phase-3-decisions-client-renderer-input.md) §12), textures <= 4096, uniform bindings <= 16 KiB, one colour attachment. Do not request above-default limits without checking `adapter.limits`.
- `checkSupport()` (`support.ts`, exported from the package root) runs before a client exists and reports why a device fails (`no-webgpu`, `no-adapter`, `limits-too-low` against `RENDERER_LIMITS`, plus non-GPU reasons); the game styles the capability screen. There is no non-WebGPU path. Tier 1 is Chrome and Safari 26+, Tier 2 Firefox desktop; only Chrome (desktop, Android) and WebKit/Firefox slow-tier runs are automated, phones are manual ([device-check skill](../../.claude/skills/device-check/SKILL.md)).
- Canvas: `configureCanvasContext` runs once per device (`getPreferredCanvasFormat()`, `alphaMode: 'opaque'`, no depth, no MSAA). `ViewportController` (`viewport.ts`) records `ResizeObserver` sizes (`device-pixel-content-box`, with a `content-box x devicePixelRatio` Safari path and a re-armed `matchMedia` for DPR changes); the next tick sets `canvas.width/height` and renders at once. Render scale = `min(DPR, scaleCap)`, default cap 2, `render.scale` overrides, clamped to `maxTextureDimension2D`.
- Backgrounding: `attachVisibilityHandling` pauses rAF on hidden; `resume()` re-checks the size and sets `FLAG_REBASE`, which the worker consumes to re-base interpolation. A hidden tab never blocks the client worker: the upload pump asks for `min(free slots, 16)` and returns when the ring is full.
- Device loss: `createGpuHost` (`gpu-host.ts`) owns the `GpuResources` (`gpu-resources.ts`: device, terrain renderer, art, drawables with atlas). Every GPU object is a cache of worker-side or HTTP-cached state. On `device.lost` it drops the resources, requests a new adapter and device, rebuilds everything (art re-fetched), notifies subscribers (the frame loop re-points the upload drain and viewport) and sets `FLAG_RENDERER_RESET`; the worker answers with `upload_requeue_all` (every resident chunk plus the indirection). While there is no device the loop keeps integrating the camera and running overlay and UI but skips upload, encode and submit. A null adapter, or a second loss within `REPEATED_LOSS_WINDOW_MS` (10 s), calls `Client.raiseRendererLost(reason)` (`'no-adapter' | 'repeated-loss'`) and the host never retries. Test hooks: `loseDevice`, `failNextAdapter` in `src/test/render.ts`.

## Frame budget and hot path

60 fps (16.6 ms), the 3-5x phone factor over desktop: main rAF callback <= 4 ms, GPU <= 6 ms, client worker `frame` <= 8 ms. Measured: GPU time means `timestamp-query` execution time of the terrain pass (`render.gpuTiming`, `gpu-timing.ts`, one frame in four), not submit latency, which is a vsync floor ([0066](../decisions/0066-phase-3-decisions-client-renderer-input.md) §1). The Pixel 5 reads 5.57 of 6 ms; re-read it after any terrain or drawable shader change. The automated desktop proxy is one third of each CPU share (main <= 1.3 ms, worker <= 2.7 ms) asserted by `bench.frame_worstcase` (65,536 drawables) and `bench.frame_reference` (the reference game scene, about 5,700-5,800 records in view, same limits) against `packages/engine/baselines/frame*.json`; diagnose with the [profile-frame skill](../../.claude/skills/profile-frame/SKILL.md). Fill-rate fallbacks if a phone misses: lower the render-scale cap (1.5, then 1), drop neighbour reads below ~4 screen px per tile, last one instanced quad per visible chunk.

The rAF path allocates nothing beyond the browser's own wrapper objects (canvas texture, view, encoder, pass, command buffer): every descriptor, scratch object and typed-array view is created once and mutated. See [hot-paths rule](../../.claude/rules/hot-paths.md) and [0016](../decisions/0016-zero-gc-definition.md). A "visible" criterion needs a pixel readback on the production page; reading the DrawList proves nothing is on screen ([0066](../decisions/0066-phase-3-decisions-client-renderer-input.md) §3). Every fixture and game page needs a viewport meta (`input/page-css.ts`).

## Gotchas

- Edit WGSL in `src/render/wgsl/*.wgsl`, then run `node scripts/embed-wgsl.mjs` to regenerate `wgsl.generated.ts` (a unit test fails when stale; `crates/engine/tests/main/wgsl.rs` runs `naga`).
- Rust-side render constants are duplicated in TS (see DrawList); a mismatch shows as garbage on screen, not an error.
- Never add a second `TripleReader` over the DrawList SAB; use `Client.pick.acquire()` once per tick.
- No GPU handle may outlive one `GpuResources`; a new GPU object belongs in `createGpuResources` so a rebuild recreates it.
- A new texture bound to terrain or drawables must go through `setTileArray`/`setSpriteAtlas`-style swapping so device loss rebuilds it.
- `extract` is `&self`: copy anything needed from input into the game's `Client` value first.
- Every GPU test asserts `RendererDevice.errors()` is empty; a device loss in a test fails it unless `allowDeviceLoss(page)` opted in.
