# Runtime and hosting

The engine ships as one npm package (`packages/engine/`, name `engine`) plus the Rust crate inside it (`packages/engine/crates/engine/`). It cannot ship a prebuilt `.wasm`: the game crate and the engine crate link into one module, so the game's build produces it. This document covers how that build runs (`build-game.ts`, `vite.ts`), what the package exports, the server entry and its Node, Bun and Deno adapters, the toolchain pins, and hosting (`games/reference-server`, Fly, cross-origin isolation). Threads, SAB, the ABI and the zero-GC budgets are in [threads-and-boundary.md](threads-and-boundary.md); the server's tick loop, sessions and wire protocol are in [simulation.md](simulation.md) and [sync-and-netcode.md](sync-and-netcode.md).

## Workspace and package

- One pnpm workspace (`pnpm-workspace.yaml`: `packages/*`, `games/*`) and one cargo workspace (root `Cargo.toml`: members `packages/engine/crates/*`, `packages/engine/fixtures/*`, `games/reference/sim`; one `Cargo.lock`, one `target/`). Profiles and the clippy `deny` setting live in the root `Cargo.toml`; the ban lists live in the root `clippy.toml` ([0017](../decisions/0017-packaging-and-build.md) §1, [0045](../decisions/0045-build-profiles-measured.md) §3). `release-names` is `release` with `strip = false`, used only by the size tests; a game's own manifest does not define it.
- `packages/engine/package.json` has `"dependencies": {}`: zero runtime npm dependencies. `vite` is an optional, types-only peer. Everything else is an exact-pinned devDependency of the root `package.json`, not of the engine. The `exports` map is closed and has no runtime conditions: `.` (client), `./worker`, `./server`, `./server/node`, `./server/bun`, `./server/deno`, `./vite`, `./render`, `./virtual` (types only), `./test`, `./package.json`. `./render` is its own subpath ([0034](../decisions/0034-provisional-render-exports-subpath.md), kept by 0045 §4). Add a subpath only together with the file that backs it.
- `files` is `dist` and `crates`: the Rust crate ships inside the package. The shipped crate manifest has literal `version`, `edition` and `[lints.clippy]` and no `workspace = true`, because no workspace root exists in `node_modules` (0045 §7). `dist/` is `tsc` output (`pnpm --filter engine build`, no bundler); `tsconfig.build.json` excludes tests.
- Not published. Packaging discipline is kept by tests: `exports-map` (unit, `src/exports-map.test.ts`) pins the map, `files`, orphan-free `dist` and the no-`workspace = true` rule; `tarball-install` (`pnpm test:slow browser -t tarball-install`, `tests/browser/packaging/`, helper `tests/support/scratch-app.ts`) packs the engine, installs it with `--ignore-workspace` into a scratch Vite app and drives dev, build and preview, a `link:` install and Node and Bun server legs.
- Rust crate policy ([0017](../decisions/0017-packaging-and-build.md) §7): the engine crate's runtime dependencies are `serde`, `postcard`, `serde_json` (argued in [0003](../decisions/0003-game-facing-api.md)), `ts-rs` (LTO removes it; the size test watches this) and `libm` only if a transcendental is ever needed; anything else needs an ADR. `serde_json`, the `ts-rs` form and `libm` were approved by Tyler, 2026-09-19. Stable Rust only (no WASM threads). The crate stays a single `engine` crate unless one of three triggers in [0067](../decisions/0067-phase-3-decisions-runtime-packaging-hosting.md) §9 fires.

## How a game crate becomes the `.wasm`

`buildGame({ crate, profile?, features?, wasmOpt?, outDir?, bindings?, env? })` in `packages/engine/src/build-game.ts` is the one build function. The Vite plugin, `pnpm test` (`packages/engine/scripts/build-fixtures.mjs`, registered in `scripts/suites.mjs`) and the server scripts all call it. No wasm-bindgen, no wasm-pack.

1. `cargo build --target wasm32-unknown-unknown` (`--release` or `--profile release-names` per `Profile`) on the game's `cdylib`, with `--features` if given.
2. If `wasmOpt` is set and `wasm-opt` is on `PATH`: `-O3` plus `WASM_OPT_FEATURES` (the strip-removed target features must be passed explicitly; `simd128`, `relaxed-simd` and `atomics` stay banned, [0002](../decisions/0002-determinism-same-wasm-everywhere.md)). Missing: a `wasm-opt-missing` warning, an unoptimised build, `wasmOpt: false` in `game.json`. wasm-opt is never an npm dependency.
3. SHA-256 of the final bytes is `buildHash`, the handshake token and log-segment stamp. A machine with `wasm-opt` and one without give different hashes, so client and server must ship from one build. A feature build lands in `target/engine/<profile>+<features>/` and has its own hash, so it never joins a normal server.
4. `game.wasm` and `game.json` (`{ buildHash, abiVersion, profile, features?, wasmOpt }`) are written beside the target and renamed into `<crate>/target/engine/<profile>/` (or `outDir`), so readers never see a truncated file. `abiVersion` comes from instantiating the module with stubs; a missing `engine_abi_version` export means `engine::export_game!` is missing.
5. With `bindings: { dir }`, `exportBindings` runs `cargo test --workspace export_bindings` (`BINDINGS_CARGO_ARGS`) and copies the ts-rs output into `dir`. Games commit the result (`games/reference/src/bindings/`).

The `.wasm` is data, never a JS import. In the browser it reaches the page as `virtual:engine/wasm`, an `EngineWasm = { url, buildHash }` object (types in `src/virtual.d.ts`, a game adds `"types": ["engine/virtual"]`). On a server, `loadGame(dir)` reads `game.wasm` and `game.json` from a `buildGame` output directory and returns `{ wasm: WebAssembly.Module, buildHash }`. Both load the same bytes; that is what makes the determinism guarantee of [0002](../decisions/0002-determinism-same-wasm-everywhere.md) hold in the field.

## The Vite plugin (`engine/vite`, `src/vite.ts`)

`engine({ crate, profile?, bindings?, wasmOpt?, features? })` imports only Node built-ins; `vite` is imported for types. It also re-exports `buildGame`, `exportBindings`, `CargoBuildError` and the build types. A game's `vite.config.ts` is one plugin line (see `games/reference/vite.config.ts`).

- `config`: profile defaults to `dev` for `vite dev` and `release` for `vite build`; `plugin.api.profile` exposes it. Sets `server.headers` and `preview.headers` to COOP `same-origin` and COEP `require-corp`, `worker.format: 'es'`, and `server.fs.allow` (the engine package's real directory, the project root and Vite's workspace root, since returning `fs.allow` replaces Vite's default).
- `buildStart` runs `buildGame` once (and awaits the bindings step). `virtual:engine/wasm` resolves to the dev route `/@engine/game.wasm?v=<n>` in dev (served by a middleware that also sets the isolation headers, `no-store`, `application/wasm`) and to an emitted hashed `game.wasm` asset in build.
- Dev rebuilds: `watchCrate` watches the game crate and the engine crate (`packages/engine/crates`) for `.rs` and `Cargo.toml`, 30 ms debounce, then sends `full-reload`; a rustc error goes to Vite's overlay as `engine:vite` and clears on the next good build. The bindings step after a rebuild is not awaited. `watchCrate` watches `src/` recursively and the crate root non-recursively and never touches `target/`: a recursive Linux `fs.watch` walks into cargo's churning scratch files and throws `ENOENT` as an unhandled error. Do not widen it. After a Rust edit the page's persisted world survives the reload ([0050](../decisions/0050-engine-failure-surface.md) §2; test `dev-reload-keeps-world @slow`).
- Worker construction: pattern A (default) is `new Worker(new URL('./worker-auto.js', import.meta.url))` inside `dist/client.js`, so a game writes no worker code. Pattern B is a two-line `worker.ts` (`import { run } from 'engine/worker'; run()`) passed as `createClient({ createWorker })`; it is the fix for a project with no workspace marker above it (worker URL outside `server.fs.allow`) and for non-Vite bundlers ([0017](../decisions/0017-packaging-and-build.md) §3).
- Tests: `src/vite.test.ts`, `tests/wasm/plugin-build.test.ts`, `plugin-dev.test.ts`, `plugin-rebuild-error.test.ts` (the `wasm` suite), `build-game-*.test.ts`.

## Server entry and adapters

`packages/engine/src/server.ts` (`engine/server`) is a library, not a process: no `node:`/DOM imports, no HTTP server, no RFC 6455 code. The host pushes connections in.

- `createWorldServer(cfg: WorldConfig, host: HostServices): WorldServer` returns `{ ready, accept(Connection), stop() }`. Loading is async: `ready` rejects with `WorldLoadError` on a corrupt or incompatible world and `createWorldServer` never throws for that. Connections accepted before `ready` are queued, with what they send meanwhile, and replayed once loaded ([0024](../decisions/0024-planning-amendments.md) §5). It throws synchronously only for `maxPlayers` outside `1..=MAX_PLAYERS_LIMIT` (8; half of `MAX_CONNS = 16` is reconnect headroom).
- `Connection` (`send(MsgClass, bytes)`, `close(code)`, `onMessage`, `onClose`, `datagrams`, `bufferedAmount?`) is the whole transport contract; `send`'s buffer is engine-owned and valid only during the call. The single-player ring transport implements the same shape. `HostServices` is `{ wasm, storage, clock, timer.every, scheduler?, onIdle?, onFatal? }`; `onIdle` fires `IDLE_MS` (30 s, `host/lifecycle.ts`) after the last player leaves, `onFatal` on an unrecoverable trap. Same code runs in the sim worker and on a server; only `Connection`, `Storage` and the clock differ ([0009](../decisions/0009-transport-and-hosting.md), amended by 0024 §5).
- `server.ts` also re-exports `importWorld`, `exportWorld`, `deleteWorld`, `ArchiveFormatError`, `WorldExistsError`, `Storage`, `buildSimInstanceConfig`, `seedToHexU64` and `WorldConfig` (see [persistence.md](persistence.md)).
- Adapters, `src/server-node.ts`, `server-bun.ts`, `server-deno.ts`, with the same names: `loadGame`, `fsStorage`, `<runtime>HostServices` and one attachment. `server-adapters.test.ts` (`server adapters export parity`) fails if they drift; a new export goes in all three. `server-host-services.ts` is the shared body (`clock` and `scheduler` from `systemClock`/`systemScheduler`, `timer.every` as a `setTimeout` chain, never `requestAnimationFrame`).
  - Node: `attachWebSocketServer(wss, server)`, which wraps each socket with `wsSocketConnection` (`server-node.ts`). The game's server package installs `ws`, builds the `WebSocketServer` and passes it in; the adapter types `WsServerLike`/`WsSocketLike` structurally and imports nothing, which is how "zero dependencies" and "the engine does not hand-roll the protocol" both hold.
  - Bun: `bunHandlers(server)` returns the handlers for `Bun.serve({ port, ...bunHandlers(server) })`. Deno: `denoHandler(server)` returns the `(req) => Response` for `Deno.serve`, built on `Deno.upgradeWebSocket`. Both are typed structurally (no `@types/bun`, no Deno lib types) and leave port, TLS, health checks and static files to the deployer ([0067](../decisions/0067-phase-3-decisions-runtime-packaging-hosting.md) §7).
  - All three share one `node:fs` `Storage` (`src/storage/fs.ts`, re-exported from `server-node.ts`), so durability cannot drift per runtime. `no-node-import.test.ts` allows `node:` imports only in `server-node.ts`, `storage/fs.ts`, `vite.ts` and `build-game.ts`; `Bun.`/`Deno.` appear only in their own adapter.
- Runtimes: Node >= 22.18 (`engines` in the root `package.json`, `.node-version` 22.18.0) and Bun 1.4.2 are tested; Deno is best-effort. Bun is pinned at 1.4.2, in `scripts/setup-tools.mjs` and CI ([0044](../decisions/0044-bun-1-4-2.md)). Tests: Bun fast-tier loopback `bun-adapter loopback` (`tests/wasm/adapter-loopback.mjs`, `wasm` suite) and the golden-hash Bun leg (`bun-leg.mjs`); `deno-adapter @slow` prints `deno-missing` and passes without Deno, and CI sets `REQUIRE_DENO=1` so it cannot skip.
- Durable Objects are not a target: a Durable Object cannot reload a snapshotted world within its 128 MB isolate, and the engine has no export for one ([0051](../decisions/0051-durable-objects-no-go.md), amending 0009). Vercel, AWS Lambda and Deno Deploy are out for the sim (0009); Vercel may serve the static client.

## Toolchain pins

Exact pins so every session, worktree and CI run builds the same bytes ([0017](../decisions/0017-packaging-and-build.md) §10; a floating channel would change codegen and `buildHash`).

- `rust-toolchain.toml`: Rust 1.93.0, target `wasm32-unknown-unknown`, `rustfmt` and `clippy`. An external game ships the same file. `.node-version`: 22.18.0. `packageManager`: `pnpm@11.25.0`. `pnpm-lock.yaml` and `Cargo.lock` are committed; npm devDependencies carry no `^`.
- `pnpm setup:tools` (`scripts/setup-tools.mjs`, `TOOLS` table) installs what npm and rustup do not manage: `cargo-nextest` 0.9.145 (`cargo install --locked`), Bun 1.4.2 (official installer) and the Playwright browsers for `@playwright/test` 1.63.0. It reports `rustup`, `node` and `pnpm` but cannot install them. It never runs implicitly: `pnpm test` only probes and tells you to run it. Bun's pin is in two places that must agree: `setup-tools.mjs` and `.github/workflows/ci.yml`. CI installs `wasm-opt` (binaryen `version_132`) only there.
- A Rust, Playwright or toolchain bump re-checks the golden hashes and the zero-GC negative controls.

## Hosting

- **Cross-origin isolation is mandatory** (COOP `same-origin` plus COEP `require-corp`, [0015](../decisions/0015-threads-memory-and-topology.md) §3). There is no `postMessage` fallback; `checkSupport` reports `not-isolated`. The headers must be on every response, 404s and worker scripts included, and on 304s. `engine/vite` sets them for `vite dev` and `vite preview`; `packages/engine/scripts/preview-headers.ts` (`previewHeaders`, repo-only, used by the two repo Vite configs, not by `engine/vite`) additionally sets `Cache-Control: no-store` on every preview response, because `vite preview` answered revalidation with a bare 304 and WebKit then refused the module worker on the second load ([0067](../decisions/0067-phase-3-decisions-runtime-packaging-hosting.md) §2). Consequences: no GitHub Pages (cannot set headers), no CORP-less third-party content, no popup OAuth; assets are same-origin.
- **Unverified: COOP/COEP on a real static host.** No third-party static host (Cloudflare Pages, Netlify, Vercel) was ever deployed to. The per-host header listings in `games/reference/README.md` come from reading each host's documentation, and 0015 §3's claim about a cross-origin `wss` was never exercised. Only the `games/reference-server --static` handler is proven (`check-coi.mjs` passes against it and the page reaches `online`), and it is a single origin ([0067](../decisions/0067-phase-3-decisions-runtime-packaging-hosting.md) §1). A static host must also send both headers on 304 responses; check each listing for that. To close it: deploy `games/reference`'s `vite build` output to one host with its listing, run `node games/reference/scripts/check-coi.mjs <url>` (asserts both exact values on `/`, the hashed worker, the `.wasm`, an image and a 404) and `DEPLOYED_URL=<url> pnpm test:slow -t deployed/` against a game server on another origin (`tests/browser/packaging/deployed-coi-and-online.spec.ts`). Until then nothing may cite a third-party host as verified.
- **`games/reference-server`** (CLI and flags: its [CLAUDE.md](../../games/reference-server/CLAUDE.md); quickstart and Fly recipe: its [README.md](../../games/reference-server/README.md)). `index.mjs` is plain Node, no build step: `ws` plus `engine/server/node`, one fixed world id per process (one server hosts exactly one world), `loadGame`, `fsStorage(--data)`, `createWorldServer`, `attachWebSocketServer`. Exit code 1 on `ready` rejecting or `onFatal`; `SIGTERM`/`SIGINT` snapshot the world and exit 0. `--exit-on-idle` exits 0 on `onIdle`. `bun.ts` and `deno.ts` are the other two entries (shared flags in `common.mjs`; no `--import`, no `--exit-on-idle`).
- **`--static <dir>`** (`static.mjs`, `staticHandler`) is a reference-server convenience, not an engine feature: `engine/server/node` stays free of HTTP. It serves the built client from the same `node:http` server, sets both isolation headers on every response it writes (200, 400, 403, 404, 405), `application/wasm` for `.wasm`, immutable caching under `/assets/`, `no-cache` elsewhere, rejects paths outside `<dir>`, and upgrades only `/ws`. It never answers conditional requests, so it never sends a 304. Page and `/ws` share one origin, so there is no CORS and no cross-origin `wss`. Test: `reference-server/static-headers` (`tests/netcode/reference-server-static-headers.test.ts`).
- **Fly image**: `Dockerfile` (`node:22-slim`, `npm install ws@8.18.3`, runs `index.mjs --data /data --static /app/client --exit-on-idle --stats-every 10`), `fly.toml` (app `engine-v2-ref`, region `ord`, `shared-cpu-1x` 512 MB, one 1 GB volume at `/data`, `kill_signal = SIGTERM`, `kill_timeout = 30`, autostop and autostart, `min_machines_running = 0`). `scripts/stage-image.mjs` fills the gitignored `.stage/` build context and refuses a client `.wasm` whose hash differs from the release build's `buildHash`, since the handshake rejects a mismatched pair. `reference-server/docker-args` keeps the three files and the CLI in agreement. No deployment is currently running; deploy and teardown steps are in the README, and `scripts/loadtest.mjs` (`games/reference-server/scripts/loadtest.mjs`) drives load against a URL. Hosting facts that are not obvious: a page load alone wakes the machine but never reaches `onIdle`; a cold wake (3.4-4.1 s) exceeds the client's dead timer so the link redials once; a save-schema change leaves the volume's world unopenable (`WorldLoadError: incompatible (MigrateDeclined)`, Fly stops restarting) until the old world is moved aside ([0067](../decisions/0067-phase-3-decisions-runtime-packaging-hosting.md) §3-§6). Cost target is about $5/month per always-on world and about $0 idle ([0009](../decisions/0009-transport-and-hosting.md)); the computed always-on figure is $3.69-4.62 plus the volume, (0009's $3.32 is unverified).
- **Budgets enforced at build/package time**: game `.wasm` <= 1 MB brotli (warn) and 2 MB (fail), release build of `games/reference`, brotli 11, in `packages/engine/budgets.json` (`size.*`), tested by `tests/wasm/size.test.ts` (`pnpm test:slow wasm -t "size @slow|ts-rs|release |wasm-opt"`; `REQUIRE_WASM_OPT=1` (read in `tests/wasm/wasm-opt.test.ts` and `feature-matrix.test.ts`) makes a missing `wasm-opt` fail). Engine JS ceiling: [0045](../decisions/0045-build-profiles-measured.md) §5. Baseline phone is iPhone 12-class or a 4 GB Android; at most 256 MB per WASM instance and a 64 MiB default world budget (see [threads-and-boundary.md](threads-and-boundary.md)).

## Gotchas

- Do not add a runtime dependency to `packages/engine/package.json`, or a `node:` import outside the allowlist in `no-node-import.test.ts`.
- `buildHash` is the identity: any change to flags, features, `wasm-opt` presence or toolchain changes it. Never serve a client and server built separately.
- A dev client cannot join a release server, by design (different hash).
- `Cargo.toml` `[profile.*]` changes move the hash and the size budgets; re-run the `wasm` slow tier.
- New suites and build steps are registered in `scripts/suites.mjs` only. Packaging and plugin tests are in the `unit`, `wasm`, `netcode` (`reference-server-*`) and `browser` (`packaging`) suites.
