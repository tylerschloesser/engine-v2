# M39s: The large-save tick has no tail

Status: done (2026-10-07; stopped at step 3) · After: 39r · Tyler-dependent: Q18 (default: the iPhone 12 is the baseline phone; the Pixel 5 is informational)

## Goal
M39o split the large-save pass and ran it on the Pixel 5 (`docs/plan/39o-large-save-tick-breakdown.md` Deviations). The pass median is 9.29 ms, already under the 10 ms ceiling of ADR 0010. The failure is a **tail inside `sim_tick`**: p50 7.89 ms against p95 23.2 ms (2.9x). On desktop Chromium the same build gives 4.57 against 5.56 (1.2x). The frame build (p95 3.8 ms), seal and resync are small, and there are no catch-up ticks. Desktop time per furnace is flat across `&scale=` 1, 4 and 16, so steady compute scales linearly; the tail is something else. Candidates (guesses, in no order): (a) periodic heavy ticks from the timer structure (a hierarchical wheel cascading a level every N ticks), or furnace completions bunched by a common start time; (b) the sim worker scheduled onto a little core of the Pixel's big.LITTLE CPU for some ticks; (c) wasm memory growth or a `BTreeMap` rebalance burst. The iPhone 12 (12.2 ms p95, M39j) has not been measured per part yet: its passcode blocks the driver.

When this is done the tail's cause is measured and named, the engine fix (if the cause is the engine) removes the measured spike, shown by a before/after per-tick series, and the orchestrator re-measures the phones. (Desktop p95/p50 is already 1.2x, so a p95 ratio on desktop can't show the fix: the criterion is on the spike ticks themselves.)

## Order of work
1. **Per-tick series.** The bench build keeps a preallocated ring of the last 4,096 `sim_tick` durations, each with its tick number. `__check.readings()` exposes a compact summary (histogram buckets, the top 20 ticks by duration with their tick numbers, and the autocorrelation peak period if any). The M39-large-save collector stores the full ring once at the end of the window in the evidence. Unit-test the summary on a synthetic series with a spike every 64 ticks: the period is found.
2. **Desktop measurement, one run**, scale 1, 60 s, headless Chromium. Paste the summary and characterise the tail: periodic or not, the period, and what the timer wheel (or other structure) does on those ticks. If the desktop tail is too small to read, also run natively (`cargo` bench or test harness at full scale) with the same per-tick series.
3. **Stop and report** with the measured cause and a proposed fix if any of these holds: the cause is not periodic engine work (scheduling or core placement: say so; the orchestrator measures it on the phone); the fix changes sim results (any golden or determinism hash); or it needs an ADR change (timer semantics, tick budget). Otherwise:
4. **Fix** the engine cause: for example, spread a cascade across ticks, or amortise a rebalance. Prove it on the per-tick series at scale 1, before and after, on the same machine and day: the spike ticks found in step 2 (for example the period's ticks, or the top 1 %) are no longer above 1.5x the median, or the improvement is stated against the before value with the series pasted and on the existing `rust`/`wasm` tick benchmarks and determinism tests (goldens unchanged).

**Seams.**
- `games/reference/src/bench-stats.ts`: `createTickRing(capacity = TICK_RING = 4096)` -> `{ push(tick, us), summary(): TickSummary, series(): [tick, us][] }`; `autocorrPeriod(x)`; `HIST_EDGES_MS` (0.5 ms wide 0.5..10, then 12, 15, 20, 30, 50; counts has one more slot for the rest); `TOP_TICKS` 20. `TickSummary = { n, missed, counts, top: {tick, ms}[], period: number | null, periodR }`. The period is the first autocorrelation peak within 3 % of the best (lags 2..512), after a 9-tick moving-average high-pass (so a slow drift is not "period 2" and a slow wave of 40 ticks is attenuated: it reports sharp, repeating spikes), recomputed every 256 ticks (about 2 ms on desktop).

Autocorrelation: lag 1 is 0.59-0.61 (the level wanders), then a **broad bump at lag 40-42 (about 2 s) and 80-82** in both runs (r 0.5 and 0.38); the 5-tick averages swing between 2.1 and 5.2 ms. The slow ticks are not phase locked: the mean by `tick mod 20/40/100` varies 3.2-4.5 / 2.2-4.7 / 2.8-4.8 ms with 12-60 samples per bin, and the top 20 ticks have scattered `mod 100` values (86, 30, 76, 55, 30, 89, ...).

**Native, same save and host (`BenchHost`, release, scale 1, 2,800 ticks after 200, scratch test deleted):** `tick` p50 1.258 / p95 1.407 / p99 1.599 / max 2.106 ms (1.12x, 9 of 2,800 above 1.5x median). The mean by `tick mod 2..64` is flat (1.26-1.29), the top ticks' `mod 100` are scattered, and the gaps between ticks above 1.25x the median are irregular (1 to 600). **No periodic engine work**: the timer structure is a `BTreeMap<Tick, Vec<EntityId>>` (`sim/timers.rs`), not a hierarchical wheel, so there is no cascade; each tick drains one bucket of about 2,621 ids and refills the bucket for `tick + 100`.

**Cause (step 3 stop applies).** The tail is not periodic engine work. The engine's per-tick cost is flat natively (1.12x), so candidate (a) is out. In Chromium the same tick is 3x the native median (3.9 vs 1.26 ms) with a broad, slowly wandering distribution (a wave of about 2 s, no phase lock to the 100-tick furnace cycle), which fits (b), the sim worker sharing and migrating between cores and contending with the client worker and GPU process (the Mac is heterogeneous too), not an engine spike. This is **not proven**: what is not separated is core placement versus a wasm-in-browser effect (cache/TLB, the shared `SharedArrayBuffer` traffic with the client worker). (c) is out on desktop: `engine_mem_grows` 0. The fix, if any, is not in the timer or the furnace system. A same-build Node `.wasm` run was tried with the net harness (`tick-large-save node`); its per-tick time covers 8 clients and a harness cadence (an exact period-4 structure, 10.8 ms median), so it is not comparable and I dropped it.

**For the orchestrator (decisions and proposals).**
1. The Pixel's 2.9x tail (p50 7.9 / p95 23.2) and the iPhone's slow median (p50 8.64 / p95 10.2) are both consistent with the desktop browser's picture: a per-tick body 3x the native cost that is wide, rather than a few spikes. Re-run both with this build (the evidence now has `tick_series` and the 0.5 ms histogram): a tail shows as a long right bin with `tick_period` null or not; a flat median shows as one narrow bin near 8-9 ms. If the Pixel's top ticks cluster in time (look at the `tick` numbers in `tick_top` and the series), it is core placement.
2. **Proposal, not built: a per-system breakdown for the median.** Native 1.26 ms vs wasm 3.9 ms on desktop is a 3x gap the engine can attack (the iPhone needs the median down by about 20 %): time the phases inside `sim_tick` in the wasm (due-timer drain, `advance`, `put_entity` and store apply, wake list) with a counter pair per phase read from the bench build only, as `CB_SIM_ONETICK_US` is. It touches the engine crate and the sim worker, and a phase counter must never feed state (determinism rule).

- **Pixel round `m39s-pixel` (orchestrator, 2026-10-07, the M39s build):** M39-large-save fail, `tick_p95_ms` 26.3; `sim_tick` p50 7.64 / p95 22.8; 36,001 ticks; `tick_missed` 7. The ring (`tick_series`, 4,096 ticks) is **bimodal**: a fast body at median 7.49 ms (3,406 ticks) and a slow mode at median 20.95 ms (690 ticks, 17 %), a ratio of 2.80. The slow fraction is even across the window (0.14-0.20 per 10 s). Slow ticks are almost all isolated (run lengths: 1 tick 493 times, 2 ticks 69, 3 ticks 10, 4 ticks 6, 5 ticks 1), and `tick_period` is null. That is core placement on wake, which a page cannot pin, and a busy-wait would be a mask. The lever is per-tick cost: a tick at 3.7 ms on a big core would fit 10 ms on a little one. **M39y** (the 3x wasm gap) is therefore the fix path for both phones.
