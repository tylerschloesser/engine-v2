- The sim worker accepts a connection only when the SAB set it boots with carries a client link (`host.connect`, topology fact), never via a test flag, and `puts_idle_100` was deliberately not re-blessed: it is `.wasm`-authoritative and read by the native Rust test from the same file, so it is the repo's one continuous native-vs-wasm equality check, and re-blessing would delete that evidence. A separate `golden-connected.json` carries the connected scenario; adding a golden is allowed, changing one is the orchestrator's call. — source: docs/plan/15b-ring-connection-and-replica-rendering.md:250 — proposed home: new ADR group "simulation"

- Chunk-coordinate ordering: never use `ChunkCoord`'s derived `Ord` (it compares `(x, y)`); the wire convention is `(cy, cx)` and every sort site uses an explicit `(c.y, c.x)` key. This was a real bug: `Replica::region_hash` iterated a `BTreeMap<ChunkCoord,_>` in `(x, y)` order while `Host::region_hash` sorted `(cy, cx)`, giving different `Fnv64` hashes for the same chunk set. Per-tick scratch sorts use a hand-written stable insertion sort (`host::insertion_sort_by_key`) because `[T]::sort_by_key` is not guaranteed allocation-free for larger inputs. — source: docs/plan/15-connection-and-subscriptions.md:163 and :176 — proposed home: line in packages/engine/crates/engine/CLAUDE.md

- `abi::arena::live_bytes()` is net (allocated minus freed), so an alloc/free pair is invisible to the `no_alloc_*` tests and a flat rise is real live growth, never "churn". M15's fix round 2 explained a 90 B/tick rise as BTreeMap node churn, which is impossible under this counter; the real causes were three unbounded Host growers (overlay map, `chunk_versions`, undrained `Cache::events`). Also: attribute gross bytes at a call site only with matched frees, and measure Host and Client separately. — source: docs/plan/15-connection-and-subscriptions.md:383 and :420 — proposed home: line in packages/engine/crates/engine/CLAUDE.md

- `Host::chunk_versions` (`BTreeMap<ChunkCoord,u32>`, ~26 B each) is never pruned and accepted as-is at M15's gate. It grows faster than world state (half its keys in the pan workload are chunks whose replicated state is empty, from an entity passing through), contradicting the brief's "stored with the chunk". The accepted ceiling is ≤ 88 B per newly reached chunk (48 B overlay Vec + ~64 B BTreeMap node on every second chunk + 26 B version entry), asserted by `host_and_client_panning_allocates_per_new_chunk_not_per_tick`; the bounded-camera test must show exactly zero per-tick growth. Check the deferred ledger copy is not the only record. — source: docs/plan/15-connection-and-subscriptions.md:459 and :440 — proposed home: new ADR group "sync/netcode"

- `Cache::events` recording is opt-in (`enable_cache_events`), enabled only where a store is paired with an `Uploader`, because the host path never drains it and it grew without bound. Chosen over a `TerrainStore::new` signature change, over `TerrainFeed`, and over self-enabling on first drain (which would silently miss earlier events). `GenQueue` therefore consults a separate always-on scalar (`invalidation_seq`) rather than draining events: a second drainer inside `frame()` would starve `Uploader::on_frame`'s `changed` flag. — source: docs/plan/15-connection-and-subscriptions.md:442 and docs/plan/15c-terrain-visibility-and-cache-invalidation.md:48 — proposed home: new ADR group "world"

- Time on a per-frame hot path: `cameraState.frameTimeMs` is a timestamp, not a delta; it feeds the 50 ms uplink rate limit and 1 s keep-alive. Production forwards rAF's own timestamp argument into `tick(tMs)` with no clock read (a nominal 60 fps `FRAME_MS` would run the uplink clock 2x fast at 120 Hz, 0.5x at 30 Hz, which Tyler's phones would show). `createResyncingClock` (`RESYNC_FRAMES = 30`) is only the fallback for `stepFrame`-style callers owning their own clock; 30 not 8, because each read costs ~12 B regardless of V8 tier once inside the closure, so 8 would have forced `main`'s budget up (a budget may go down, never up). Remaining boxed doubles: `ManualClock.advance/frame` and `stepSimTickSync`'s Atomics, absorbed by larger budgets. — source: docs/plan/15d-client-clock-allocation.md:118 and :14 — proposed home: line in .claude/rules/hot-paths.md

- A correctness fix nothing exercises is the repo's most repeated defect (five instances: M14, ADR 0029, M13's dead counters, M09b's probe grid, ADR 0030's `poll()` guard). Rule applied: every such fix needs a test that fails when the fix is reverted, shown by fault injection (revert, observe the number, restore); e.g. the `wokenBy === lastWokenBy` guard test reads 47-48 ticks reverted versus 26-27 with the guard, bound `[0.5x, 1.35x]` of 30. Likewise a test that asserts `expect(true)` or whose only measured control is never injected does not count. — source: docs/plan/15b-ring-connection-and-replica-rendering.md:300 and docs/plan/15e-paced-tick-measurement.md:150 — proposed home: new ADR group "process"

- `SimHostCounters` (all of them) are cumulative from `simHost.start()` and nothing resets them; a browser test comparing a counter against a windowed expectation must take two readings and assert the delta. A single end-of-window read measures lifetime, and the error grows with how slow the machine is before the window opens, which hid it locally (26 ticks) and failed CI (79-83). `__simCounters` parks and resumes workers; the resume adds exactly one tick (accounted for within the 1.35 ceiling). — source: docs/plan/15e-paced-tick-measurement.md:181 — proposed home: line in packages/engine/CLAUDE.md

- ADR 0030's "bounded at one window and self-correcting" claim holds in one direction only: `resync()` corrects the sim only when behind (`overshoot > 0`) and has no branch for running ahead, so anything that made `poll()` fire faster than the tick rate would run the sim fast uncorrected. Not reachable today (measured error is the other way: external wakes suppress polls). — source: docs/plan/15e-paced-tick-measurement.md:96 — proposed home: new ADR group "simulation" (amend 0030 with a one-line caveat)

- `Delta::Ack { who, seq }` and `Delta::Roster` are engine-only `Delta` variants: `Ack` is applied straight to `Store` via `Authority::record_ack`, bypassing the `ChangeLog`, so it never appears in a client-facing frame (0004 delivers acks on their own channel); every exhaustive `match` over `Delta` in the frame builder has an explicit empty `Ack` arm with a stated reason, never a catch-all. `Delta::Roster` with no player slot is a silent no-op (apply stays infallible and idempotent). `Store::next_entity_id` tracks `max(applied id)+1`, so replay reproduces ids. — source: docs/plan/12b-world-access-and-sim-driver.md:90 and docs/plan/15-connection-and-subscriptions.md:159 — proposed home: new ADR group "sync/netcode" (amend 0024 §7/§8 and 0022)
