## runtime/packaging/hosting

## client/renderer/input

- GPU time is judged from `timestamp-query` execution time, not submit-to-`onSubmittedWorkDone` latency: the latter is a vsync floor (a trivial flat full-screen pass reads 12.9 ms p50 on the Pixel while its timestamp delta is 1.18 ms), which is why no scale cap ever moved the old 12-19 ms readings that "failed" the 6 ms limit of 0018 §9. After the change the Pixel passes M09b at 5.57 ms of 6 (thin margin: anyone changing the renderer should re-read it) and the iPhone reads 3.85 (0.69 with anchors). Timestamps showed no coarse clamping on either phone. The terrain pass only is timed (drawables ride in it via `onEncode`); the standalone `drawables.draw` pass is not. Option is `render.gpuTiming`, default off, so the shipped device request stays empty. — source: docs/plan/39k-gpu-exec-metric.md:Goal, Deviations "Seams" and "Driven rounds" — proposed home: new ADR group "client/renderer/input" (amends 0018 §9 wording "GPU latency" to "GPU execution")
- Every fixture page lacked a viewport meta, so before M39h every phone reading from a fixture page (M09b fill-rate, M11, and others from M09b on) was taken at the browser's 980 CSS px desktop layout (Pixel canvas 1960x3999, iPhone visualViewport scale 0.398). The helper now writes `width=device-width, initial-scale=1, viewport-fit=cover`; pages that do not call it carry the static tag, and pages that do carry it too because a meta inserted after first layout may not take effect everywhere. `user-scalable=no`/`maximum-scale` are deliberately not added (0019 §3 stops page zoom with `touch-action` and `preventDefault`, not by disabling accessibility zoom). Any phone number recorded before 2026-10-05 is at the wrong size. — source: docs/plan/39h-mobile-viewport.md:Goal, Scope 1-2 — proposed home: new ADR group "client/renderer/input" (amend 0019 §3: "never disable user scaling" and "static tag on game pages")
- Chrome Android's touch adjustment snaps a tap near a drawn ring to its overlaid DOM button (`elementFromPoint` says canvas, the real target is the BUTTON): M18-pick cannot be completed on a 392 px Pixel at 40 tiles (11 px under the ring's anchor picks it, 9 hits the button, 15 misses), so a real player has the same problem there. It passes on the iPhone. Recorded as a finding and left unresolved. — source: docs/plan/39j-device-driver.md:171 (finding 2), :221 (finding 12) — proposed home: new ADR group "client/renderer/input" (known limitation of overlay buttons over picked entities on small Android screens)

Not an engine defect; the walk agent clears keys with that prefix when the URL has `_fresh=1`, except `M23-kill-resume` (`plan.keepCamera`), which needs the restore. — source: docs/plan/39j-device-driver.md:69, :88 — proposed home: drop: agent.js and a unit test pin it (the prefix is derived from `cameraStorageKey`)

## sync/netcode

- A remote that is connected but silent never fades: the host re-relays held presence samples at >= 1 Hz (`refresh_presence`), so the "silent drop fades after ~2 s" path of 0013 only triggers when the relay stops (a stalled link). A clean close sends `PresenceRelayOp::Gone` and the circle vanishes at once (measured 116-215 ms). The M34-remote-motion check therefore tests "vanishes within 1000 ms", not a fade; `remote-fade.spec.ts` covers the real fade with a TCP proxy holding server-to-client for 2.6 s (< `DEAD_MS` 3000, since CDP `emulateNetworkConditions` could not reproduce a silent drop headless). — source: docs/plan/39l-remote-motion-staircase.md:Diagnosis, Differences 2 — proposed home: new ADR group "sync/netcode" (amend 0013/0040: when the fade can occur)
- The own-timer completion gap is confirmed by measurement on loopback: the host's result arrives 112-517 ms after the bar is full (bar median 1550 ms; `ui/collect.ts` sizes the bar from `done_at - clock.predicted`, the result comes `lead` later), exactly the "bar full, result waiting" failure the device item names; 0012 deferred this to Phase 2 ("accept it...") and it was routed to the deferred ledger as M26's. The check's tolerance (`plan.timer.toleranceMs` 100 = one 20 Hz tick plus two frames) is a measurement resolution, not a Pass number. — source: docs/plan/39f-device-auto-runner.md:376, :389 — proposed home: new ADR group "sync/netcode" (settle 0012's deferred own-timer gap: accept/mitigate; the ledger row is deleted with docs/plan)
- A late-joining client previously lagged interpolation by (host tick x 50 ms)/10 for the whole session (about 17 s behind at a 19 s world; a day-old world would not converge in the first hour) because `HostClock` was seeded from the empty replica's tick 0 and then slewed at the 10 % dilation limit. Fixed by snapping once on the first real host tick (`host_clock_primed`); the netcode suite never saw it because its observers join at tick 0. Delay, extrapolation cap and `HostClock`/`InterpBuffer` unchanged, so 0012/0040 behaviour is unchanged. — source: docs/plan/39l-remote-motion-staircase.md:Deviations "Cause", "Fix" — proposed home: drop: the `host_clock_primed` doc comment names the cause and `interpolation/late_joiner_remote_moves_every_frame` pins it
- `Client.onLink`/`onUi`/`onStorage`/`onResyncing` do not replay to a late subscriber: register every `client.on<Name>` before the first `await` after `createClient` (the check-build `installCheck` subscribed after `startGame`'s awaits, so `link` stayed `none` and M34-two-devices "never joined" on both phones through five rounds; the real cause was subscription order, not the tunnel or COEP). `StartGameOptions.onClient` exists for this. `client.ready` must also get a `.catch(() => {})` right after `createClient` or a refused start (`world-busy`) is an unhandled rejection whenever GPU setup is slow. — source: docs/plan/39n-two-devices-join.md:Fix round 2, docs/plan/37b-device-loss.md "CI gate correction"; docs/plan/37-robustness-events.md:115 — proposed home: line in games/reference/CLAUDE.md (next to "`status.ts` the one place")
- `onFatal` after a server-side fatal adds no protocol: clients reconnect with backoff until a fixed build answers with version mismatch. A close code that stops reconnecting would strand players when a supervisor restarts the world with the fix. (Decision text in 0050 §4; the *reason* is there too.) — source: docs/plan/37-robustness-events.md:62 — proposed home: drop: ADR 0050 §4 states it

## persistence
