# Handoff sweep: briefs 39o-39aj (late Phase 3 device-round fixes)

- On the Pixel 5 and iPhone 12 the large-save tick costs about 3x the native tick because of the wake after the sim worker's idle sleep, not because of wasm, Chromium tiering or the allocator. Measured by M39y: the same release bench `.wasm` in Node is 1.7 ms ticking back to back (1.3x native 1.3 ms) and 3.65 ms with a 50 ms sleep between ticks (Chromium 4.19), every phase slowing 2-3x together, with the browser's p95/p50 shape. The cause is a core and caches gone cold in the idle gap (clock, L1/L2, TLB), the same mechanism as the Pixel's little-core wake. Native and wasm builds use the same root `[profile.release]`; only the allocator differs. ADR 0056 cites "M39y's cold-wake finding" and these briefs, which Phase 4 deletes. Without this a session will chase a wasm-specific fix. — source: docs/plan/39y-wasm-tick-cost.md:Deviations "Step 1" and "What carries the gap, and the mechanism" — proposed home: new ADR group "simulation" — captured in docs/decisions/0063-phase-3-decisions-world-and-simulation.md §11

- The large-save tail is not engine work. Natively the per-tick cost is flat (p50 1.258 / p95 1.407 ms, 1.12x, mean by `tick mod 2..64` flat). The timer structure is a `BTreeMap<Tick, Vec<EntityId>>`, not a hierarchical wheel, so there is no cascade, and nothing is periodic or phase-locked to the 100-tick furnace cycle. The Pixel's bimodal ticks (fast mode 7.5 ms, slow mode 21 ms, 17 % of ticks, mostly isolated) and the desktop's wide body (2-5.5 ms) are scheduling, and a page cannot control that. This is the evidence behind ADR 0056 §3 (Pixel reported, not judged). — source: docs/plan/39s-sim-tick-tail.md:Deviations "Native, same save and host" and "Cause"; docs/plan/39y-wasm-tick-cost.md:Deviations "Context from the orchestrator" — proposed home: new ADR group "simulation" (same ADR as the cold-wake bullet) — captured in docs/decisions/0063-phase-3-decisions-world-and-simulation.md §12

- In the large-save pass `sim_tick` is about 90 % of the whole sim-worker pass on desktop. Cost per furnace is flat (17-18 ns) from 1/16 to full scale, so it is compute bound, not cache bound. - Built and not built for the 10 ms bar (M39y, M39ae, M39ag). Built: timer buckets as `VecDeque` (the old `Vec::remove(0)` moved about 13 MB of ids per tick; about 10 % of the median); dense `by_entity` table capped at `DENSE_LIMIT` 2^20 ids because ids come from an untrusted snapshot (paced p50 down to 78.9 %); in the frame path, per-chunk entity iteration and snapshot caching (whole pass p50 down to about 87 %). Tried and dropped: an id-indexed table for `upsert_entity_op` gave no measurable gain (build p50 0.625 vs 0.625) and, because it grows with the largest entity id, pushed `host_and_client_panning_allocates_per_new_chunk_not_per_tick` over its ceiling (89.49 B vs 88). Not built, the room left if the phone is short: `chunk_versions.insert` dedupe, a `put_entity` write path (each furnace is put once per tick, so "already recorded this tick" skips nothing), and moving the entity table (`BTreeMap<EntityId, Entity>`, `store/mod.rs`, a quarter of native tick samples) off a BTreeMap, which is a storage change (Q18 (c)). Dedupe of the double encode of the collapsed chunk across ticks is also open. — source: docs/plan/39ae-large-save-tick-under-10ms.md:Deviations; docs/plan/39ag-large-save-pass-margin.md:Deviations "Tried and dropped", "Not done" — proposed home: new ADR group "simulation" — captured in docs/decisions/0063-phase-3-decisions-world-and-simulation.md §14

- Remote interpolation fix (M39ab). A remote at rest holds one old sample, so on the first new sample `render_t` falls at u of 0.95-0.99 of a very long segment and the cubic Hermite draws the circle up to about 1 tile behind `b.pos - V*delay`, then glides forward (-1.094 tiles on the Pixel). Chosen: clamp each end's tangent per axis, `|h*v| <= 3*|delta|` (Fritsch-Carlson), for stale segments only, in `InterpBuffer::sample`. Rejected: (b) a relay-interval constant that treats a long segment as starting from a synthetic rest sample, because it needs a constant; and the first version, which clamped every segment, because it zeroes the tangents of a flat segment and would fail the rest-then-walk case. An ordinary 10 Hz walk (|h*v| 0.4 against 3*delta 1.2) is bit-identical to the unclamped curve. Side effect: the velocity returned across a clamped knot is not C1 (only `pos` is drawn). 0012's stated method is unchanged; no ADR was written. — source: docs/plan/39ab-remote-lurch-after-rest.md:Deviations first bullet and last bullet — proposed home: new ADR group "sync/netcode" (amends 0012 "Remote motion") — captured in docs/decisions/0064-phase-3-decisions-sync-and-netcode.md §25

- Resources are `COLLECTABLE` only, and a furnace can be placed over one. Covering is derived, not stored: trait `COVERS_RESOURCE` (`1 << 2`) on the furnace prototype, and a tile is covered whatever `traits_at` reports through its occupant term. This keeps it right after load, after pick-up and in the predicted path, with no bookkeeping and no encoded-state change. A collect in flight when a furnace lands ends with no item and no depletion; `StartCollect` on a covered tile gets `RefReject::NoResource`. Alternative of a stored flag rejected (state, encoding and prediction cost). Tyler's answer drove it. — source: docs/plan/39ai-tyler-answers.md:Deviations "R1 design" — proposed home: new ADR group "world" — captured in docs/decisions/0063-phase-3-decisions-world-and-simulation.md §6 (also games/reference/CLAUDE.md Placement bullet)
