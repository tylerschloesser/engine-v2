- Own-timer completion gap rule is "stretch" (Tyler's Q10 answer): `own_progress` runs over `duration + lead` (about 7 % slower for a 2 s timer at 150 ms), so the bar fills when the host's result can arrive. Measured gap 0 ticks versus `lead` for the plain predicted clock at delays 0, 1 and 3. Opt-in predicted expiry stays rejected (it would be a client-side tick rule). Landed formula uses `effective_lead = lead - correction` in both terms, because the brief's literal `done_at - correction` leaves a k-tick jump at the ack. — source: docs/plan/26-prediction-rendering-and-clocks.md:47-49 and Deviations (~:360-380) — proposed home: new ADR group "sync/netcode" — captured in docs/decisions/0064-phase-3-decisions-sync-and-netcode.md §2
- Lead and host-clock choices: lead is the median of the last 8 ack samples (`ack.tick - auth_tick_at_dispatch`, pure tick arithmetic, no wall clock), clamped to 1..=40 ticks, seeded `ceil(rtt/tick)+1`. A median was chosen over a mean because one outlier of 40 moved the mean. `HostClock` lives in M26 and samples every arriving frame, taking the maximum offset over a 2 s window and slewing at the 0010 dilation limit, never stepping except `rebase()`. Reason: idle ticks send no frames, so a clock that only steps on frames would freeze bars for up to a heartbeat. — source: docs/plan/26-prediction-rendering-and-clocks.md:44-46 and :375-390 — proposed home: new ADR group "sync/netcode" — captured in docs/decisions/0064-phase-3-decisions-sync-and-netcode.md §3
- A pending tile is styled by the game, not the terrain shader. The texel carries only the predicted value; the game draws a `rect` or `ghost` from `predicted_tiles`. Reason: `TileTexel` has no spare meaning and the terrain shader has no per-game styling hook, while the DrawList has both. Entities carry a `PREDICTED` flag set by `extract`. — source: docs/plan/26-prediction-rendering-and-clocks.md:43 — proposed home: new ADR group "client/renderer/input" — captured in docs/decisions/0066-phase-3-decisions-client-renderer-input.md §9

- `Replica::entity` returns `Err(Unknown)` for an unseen real id, `Ok(None)` for a provisional id, and `Predicting::entity` short-circuits provisional ids before asking its base. `View::entity` deliberately stays unchanged. Reason: `View` serves both the host-total reading (a despawned id must stay `Ok(None)`, there is no "Unknown" on an authoritative host) and the client subscription reading. The change flipped three older tests' assertions from `Ok(None)` to `Err(Unknown)`, caught only by a workspace-wide nextest run, not by `fx-predict`. — source: docs/plan/25-prediction-core.md:208-228 — proposed home: new ADR group "sync/netcode" (amends 0022 §7) — captured in docs/decisions/0064-phase-3-decisions-sync-and-netcode.md §4
- Prediction-test gotchas. (a) A scenario needs a second client sending `SetGlobal` every tick from before warm-up (`warm_up_with_noise`). Otherwise the per-client delay queue is full of empty frames and the first non-empty frame also carries the ack, so the replay loop never runs and the mutation check (`frozen_predicted_tick`) passes vacuously. (b) `predict_alloc` must compare `high_water_bytes` against a mark taken before the first replay call, warm-up included: a uniform per-call allocation banks its peak in warm-up and is invisible to a mark taken only around the measured window. (c) A game whose `apply` panics (`fx-panicky`) must opt out with `Game::predict -> false`, because `ClientCore` now runs `apply` client-side for every game. — source: docs/plan/25-prediction-core.md:155-180, :197-206, :318-327 — proposed home: line in packages/engine/crates/engine/CLAUDE.md — captured in .claude/rules/prediction.md (prediction scenarios need a second client sending SetGlobal)
- The Hello camera report is never copied into `ConnSlot.camera`. `client_hello()` sends a well-formed zeroed report, so `CameraReport::read` succeeds. - Ack tracking stays dependent on the game calling `put_player` in `on_player(Joined)`. A game that does not gets `ack_seq` and `last_processed_action_seq` stuck at 0, so resend and `Lost` do nothing useful. Rejected: (a) an engine-tracked per-connection seq moved out of `PlayerSlot` changes `Store`'s canonical encoding for every game and re-blesses every golden; (b) the engine creating the slot itself is impossible because `G::Player` has no `Default` bound and adding one is a `Game`-trait change with the same golden blast radius. - Resync mechanics. A second `Welcome` on an attached connection is the resync signal (no new message type), the epoch lives in the manifest, and it bumps on every host start over an existing world (not only after `recover()`). `client_on_welcome` resets the replica and overlay only when `welcome.epoch` differs, so a same-epoch reconnect keeps chunks and the 3-byte "keep" resume works. The pending queue is never cleared: unacked actions are resent, and those at or below the ack seq are reported `Lost`. `onRecovered` is wired per call site, not as a default, because a blanket default silently changed behaviour for callers that build a raw `SimHost`. — source: docs/plan/28b-reconnect-and-lifecycle.md:45-47 and Deviations (Part A, Step 3) — proposed home: new ADR group "sync/netcode" (amends 0013 / 0024 §8) — captured in docs/decisions/0064-phase-3-decisions-sync-and-netcode.md §14

- Handshake determinism gotcha. `crypto.subtle.digest` completes on Node's libuv pool in unseeded order, so two simultaneous joiners swapped `PlayerId`s between runs of the same seed. Fix: a promise chain (`sessionMutationChain`) in `Hello`-arrival order, and the harness awaits `handshakesSettled()` each tick (a plain `advanceBy` never gives the digest a turn). Separately, `Reject` only follows a parseable `Hello`; unparseable messages count as garbage (cap 8, then `ProtocolError`, or 5 s with no `Hello`). — source: docs/plan/28-sessions-and-reconnect.md:276-291, :145-150 and :170-176 — proposed home: line in packages/engine/tests/netcode/CLAUDE.md — captured in packages/engine/tests/netcode/CLAUDE.md (crypto.subtle.digest paragraph)
- `ws` harness ordering. Different sockets deliver in OS-poll order, so recording arrivals as they happen made `trace()` differ between runs of one seed (spike C failed). Close frames must be counted, or `advanceTicks` ends before a 4002 close arrives. Spike C result: 3 runs of 200 ticks, 4 clients and a mid-run reconnect gave byte-identical traces, so no downgrade to a smoke test. `ws/reconnect-resume`, `ws/trace-identical` and spike C are `@slow` because the `ws` subset added about 10 s to the fast netcode suite. — source: docs/plan/30c-ci-reds-after-m30.md:Deviations B and CI round 1; docs/plan/29-net-worker-and-reference-server.md:94-96 — proposed home: line in packages/engine/tests/netcode/CLAUDE.md — captured in packages/engine/tests/netcode/CLAUDE.md (ws harness releases arrivals sorted by a global send sequence)
