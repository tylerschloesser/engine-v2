# Handoff sweep: briefs 20 through 24c

- Admit-phase panic recovery answers the action `Rejected(Engine(EngineFault))` through a dedicated export, `sim_fault_ack(conn, seq)`, which also raises that connection's `highest_admitted_seq` to `seq`. An `Admit` trap is never logged, so replay never revisits it and `pending_fault_acks` (the `ApplyRecord` mechanism) cannot apply; the `ProgressCursor` carries `seq` in `record` but no connection, so `SimHost` tracks `inFlightAdmitConn` around each `simAdmit` and reads it from the dead instance before rebinding. Without the dedup-floor bump a client resending after resync re-trips a deterministic `PanicInAdmit` and the loop guard (3 recoveries without 1,200 good ticks) turns one bad action into a fatal stop. The clearing of `inFlightAdmitConn` and the `Phase.Admit` gate each mask a failure of the other, so both stay; the test must check ack content, not a specific `seq` (a stale ack carries `seq: 0`). 0050 lists the `EngineFault` result but not this mechanism. — source: docs/plan/24-recovery-and-migration.md:473 (also :236 gate note, :605 on `recovery_loop_guard`) — proposed home: new ADR group "persistence" (amends 0005 Panic recovery)

- A `SCHEMA_VERSION` difference goes to `Game::migrate` in either direction, and `Identity::compare` never returns "incompatible" (no such variant). An early revision returned `Incompatible` for a stored schema newer than the running build; the gate overruled it, because accepting a newer save written by a newer build is the game's call (a game that supplies a `migrate` accepting `from_schema == 2` on a v1 build is legal; the default `migrate` yields `SaveIncompatible { MigrateDeclined }`). Related limits: a world with no snapshot yet can only be `Same`/`Direct` loaded, never migrated across a schema, tick-rate or worldgen change (there is no snapshot container to build an `OldStore` from), and the genesis-only path asks Rust (`sim_identity_compare`) rather than keeping a TS copy of the matrix, because a TS mirror had its `TickRate`/`Worldgen` branches swappable with all 144 wasm tests green. A non-empty but undecodable segment-0 header is `WorldLoadError('corrupt')`, never treated as "same". — source: docs/plan/24b-upgrade-and-migration.md:107 (gate :529, genesis fallback :447, :483) — proposed home: new ADR group "persistence" (amends 0005 Upgrades / 0024 §3)

- Upgrade identity is compared per snapshot candidate against that candidate's own decoded identity, never against `manifest.created`, which only records the original creation identity and would re-trigger the upgrade path on every ordinary reload after the first. `WorldLoadError` kind `'identity'` is now dead (nothing throws it); `'incompatible'` replaces it. `packages/engine/src/host/CLAUDE.md` still describes the old behaviour ("Checks the running identity first ... against `manifest.created`, throwing `WorldLoadError` on a mismatch"), so it is stale and should be rewritten with this. — source: docs/plan/24b-upgrade-and-migration.md:352 — proposed home: line in packages/engine/src/host/CLAUDE.md

- OPFS latency on real devices is measured and closes the deferral in 0005 ("OPFS append/flush latency on iOS Safari ... only tunes the 1 s sync interval"): iPhone (iOS 18.7, Safari 27.0.1) `flush` p95 0.1 ms, `append` p95 0.02 ms, 8 MiB scratch write p95 8.3 ms; Pixel 5 `flush` p95 0.255 ms, 8 MiB 39 ms; `move()` and `navigator.locks` present on both. The 1 s sync interval therefore stays. The retune rule that was fixed in advance, so a future regression is not re-argued: `flush` p95 <= 10 ms keep 1 s; 10-40 ms raise to 2 s (power-loss window then equals the object-store row); > 40 ms (longer than the tick gap) `sync` only at snapshots and clean boundaries; `append` p95 > 2 ms is reported but changes nothing; any change is a new ADR superseding that number in 0005. These numbers live only in `device-checks.md`, which Phase 4 deletes. — source: docs/plan/23-persistence-opfs-and-lifecycle.md:56 (numbers: docs/plan/device-checks.md:188-189) — proposed home: new ADR group "persistence" (closes 0005 Consequences deferral)

- Replay/heavy-mode hash comparison cannot catch two classes of defect, so do not trust a green hash test for them: (a) "restore silently reuses the live instance" (a fixture with no hidden state reproduces the same hashes either way; the proof that restore really decodes bytes is a corrupted-snapshot injection that must fail with `sim_restore_push` status `Corrupt`), and (b) a self-consistent relative-encoding error (the segment-open reset of `last_logged_tick`, `log_ref_tick`) where writer and reader share the same wrong reference and the errors cancel; removing the `sim_segment_header` reset passes every test (no byte golden pins a two-segment log). Also: the fast-tier heavy test (N=25) needs a state-dependent action (`Roll`) placed well past several N boundaries, otherwise dropping the restored `SimRng` passes. Anyone touching `sim_segment_header`, `sim_restore_end` or heavy mode should know the reset is still required (Planning decision 2's per-segment base bookkeeping) though untestable by hash. — source: docs/plan/22-persistence-log-and-snapshots.md:245 and docs/plan/22b-persistence-load-and-fs.md:286 — proposed home: line in packages/engine/crates/engine/src/persist/CLAUDE.md

- Vitest footgun, found independently twice: never pass an `EngineInstance` (live `Uint8Array` views over WASM memory) to `expect()`, and never use `expect(promise).rejects.<matcher>` on a promise that might unexpectedly resolve with one. Vitest eagerly pretty-prints both operands even on a passing `not.toBe`, climbing past 4 GB and dying with `SIGABRT`/"Reached heap limit" with no assertion message, which looks exactly like an infinite loop in product code. Compare with `===` / plain property reads, or convert the settlement to a plain value first (`expectIncompatible` in `upgrade.test.ts`). Currently only noted at the top of one test file. — source: docs/plan/24-recovery-and-migration.md:236 and docs/plan/24b-upgrade-and-migration.md:377 — proposed home: line in packages/engine/CLAUDE.md

- Engine-edit rebuild time: M24c's attribution overturned the brief's premise. Compile and link are about 27-30 s; the rest was macOS's one-time first-execution security check on every freshly linked executable (1.25 s first run vs 0.007 s second; 10 fresh binaries serially 29.4 s), paid once per test binary because `cargo test --workspace export_bindings` executes every workspace test binary even when the filter matches none. Consolidating `crates/engine/tests/` from 25 files to 13 binaries (`tests/main.rs` + `tests/main/*.rs`, guard `scripts/lib/engine-test-binary-layout.test.mjs`) cut a `touch lib.rs; pnpm test unit` rebuild from about 210-230 s to about 147 s; 67 binaries remain, 43 of them fixtures and `reference-sim`, and consolidating those too was estimated to reach only about 100 s. Alternatives measured and rejected: restricting `exportBindings` to `--lib` (the cost just moves to the next build step, 44.8 s then 107.7 s) and running fresh binaries in parallel (only about 2x). The out-of-repo lever is macOS's Developer Tools exemption for the launching terminal (`sudo spctl developer-mode enable-terminal`, then System Settings > Privacy & Security > Developer Tools): Tyler's to enable, never measured; no budget ADR until measured with it on. Caution: these figures predate 0048 (`split-debuginfo = "packed"`) and 0049 (45 s from `pnpm measure:rebuild`, 37.6 s for an engine edit); reconcile the two measurement paths before using either as the baseline. — source: docs/plan/24c-engine-edit-rebuild-time.md:69 (gate :99) — proposed home: new ADR group "testing/tooling" (amends 0049 Context)

- Overlap is deliberately not rejected by the engine: no debug panic on a put whose footprint covers a tile already occupied by another entity. `ChunkIndex` is overlap-tolerant (`entity_at` answers the lowest id, `overlapping()` lists every id) and `Registry::prototype_traits`/`footprint` are total (unregistered id gives empty traits and a 1x1 footprint). Why: the debug-assert was built and removed because roughly a dozen pre-existing test `Game`s use a fixed `anchor`/`PrototypeId(0)` stub and panicked on the second spawn; per "never weaken an existing test" the assert was dropped. Real games prevent overlap with the "ask the tiles" convention (`can_place` via `traits_at`, plus a game-side overlap guard test). A future "add the missing overlap assert" would re-break that fleet. — source: docs/plan/21-entities-and-timers.md:140 (ledger row :258) — proposed home: new ADR group "world" (amends 0007 §6)

- `Ui.in_range[].from` is stamped at tile-entry time (the player's position when the tile entered range, refreshed only when the set changes), so `Ui` changes at tile-crossing rate and never per frame. Alternatives rejected: a `ClientSide` hook that stamps actions (a new `Game` API needing an ADR) and reading an anchor slot from TypeScript (f32 precision far from the origin). `from` is a real position of the player, inside `RANGE` of its tile by construction and at most `2 x RANGE` from the live presence sample, far inside the `admit` tolerance (16 tiles). `games/reference/CLAUDE.md` states the rule but not the rejected alternatives or the bound. — source: docs/plan/20b-reference-player-and-collect-ui.md:44 — proposed home: line in games/reference/CLAUDE.md

- Collects are not reservations: two players may collect one tile at once, and at completion a collect whose resource is gone ends with no item (the tile is re-read at completion, not trusted from `apply`). Why: keeps `apply` free of cross-player reads and produces the "last unit" rejection race that 0003 Consequences wants scripted (M34c). Player collect timers are scanned from the player table (`done_at` compared in `tick`), not scheduled on the engine timer wheel. Neither is stated in `games/reference/CLAUDE.md` or the spec. — source: docs/plan/20-reference-game-v0.md:39 — proposed home: line in games/reference/CLAUDE.md

- The reference zero-GC page certifies `RefClient::ui()`/`extract` (client worker, strict 8 B/frame) and the overlay's panning writes (`main`, 234 B/frame budget, 213 in software mode) but not the DOM layer: `collect.ts`/`inventory.ts` `onUi` is polled on the real rAF, which never fires inside the synchronous `drive()`, so the two buttons sit static for the 600 measured frames. Accepted because the exit criterion names the client-worker budget and `onUi` runs at state-change rate. Do not read a green `gc-reference` as proof the DOM code is allocation-free. — source: docs/plan/20b-reference-player-and-collect-ui.md:469 — proposed home: line in games/reference/CLAUDE.md

- Correction to a surviving line: `games/reference/CLAUDE.md` says "`minify: false` in `vite.config.ts` is load-bearing". The orchestrator fix at the M20b gate restored minification in the production build; only the test build step (`scripts/suites.mjs`, `vite build --minify false`) disables it, because software-mode zero-GC attribution matches runtime function names (`attributionRoots: ["drive"]`) and a minified build silently reads a flat 0 B/frame even under the `object` negative control. A minified build makes the `neg object main` control stop tripping under `GC_MODE=software`. — source: docs/plan/20b-reference-player-and-collect-ui.md:418 (gate :472) — proposed home: line in games/reference/CLAUDE.md (fix the existing line)

- `stepTick`/`untilQuiescent` settle on the rings a worker or `Client` actually drains and deliberately never on `client.uploadRing`; M20c's cause was that `ringSabs()` waited on a ring only a page's renderer drains, so on a connected manual-clock page `untilQuiescent` timed out at 10 s while the client worker was never stuck (`W_ACK === CB_FRAME_REQ`). The brief's premise ("the client stops acking") was wrong; the diagnostic signature separating this from the `parkWorkers` watch item is `W_YIELD: 0` and `untilQuiescent: timed out`, deterministic, versus `W_YIELD: 1` and `parkWorkers: timed out` intermittent under load. Removing the ring changed timing so `connected-terrain.ts` (whose 16 ms interval had incidentally been given time to run) flaked 2/8 until its `__advance` drained the upload ring itself; any manual-clock page that reads pixels must drain uploads synchronously. The `packages/engine/CLAUDE.md` line names the contract but not this flake mechanism or the watch-item signature. — source: docs/plan/20c-client-ack-freeze-under-untilquiescent.md:136 (gate :227) — proposed home: line in packages/engine/CLAUDE.md

- Stepped-browser-page gotchas found live and not all recorded: (1) `stepTick`/`untilQuiescent` park every worker on return, so any later `stepFrame` hangs until `resumeWorkers`; (2) a dispatched action sits in the client's action ring until a `stepFrame` flushes the uplink, so `stepTick` right after `dispatch` makes later actions arrive together and reject all but the first `Busy`; (3) the real host queues an admitted action for the tick after it arrived (0004 "T+1"), so a 40-tick collect completes after 41 ticks in the browser but exactly 40 natively (`RefScenario` applies in the same `Sim::step`), hence `COLLECT + 1` per round in `depletion.spec.ts`; (4) `engine/test.lastUi`'s subscription is lazy, so prime it once straight after `openGame` or an early delivery is lost for good; (5) fixed-count `stepTick`/`stepFrame` sequences flake under load, poll a `uiState` condition (`pumpUntil`). — source: docs/plan/20b-reference-player-and-collect-ui.md:129 (and :288, :306) — proposed home: line in packages/engine/CLAUDE.md ("Adding a browser spec")

- A test that derives its numbers from the constant under test cannot fail when that constant changes: `recovery_loop_guard` built its loop counts from the exported `RECOVERY_LOOP_LIMIT`/`RECOVERY_GOOD_TICKS_RESET`, so changing the limit 3 to 4 still passed; it now pins the literals 3 and 1,200. Related measurement limit: `tick_state_steady_no_alloc` compares net live bytes over a short and a 5x longer window, so an alloc-then-immediate-free pair (the original `ChunkIndex` churn bug) is invisible to it; per-call allocation needs a `no_alloc_*` counting-allocator test. — source: docs/plan/24-recovery-and-migration.md:605 and docs/plan/21b-timers-wakeups-and-tickcx.md:221 — proposed home: line in .claude/rules/hot-paths.md

- `OldStore::decode` re-implements `Store::write_canonical`'s reader side byte for byte (players, next_entity_id, global, overlay, entities, active lists, timers, wake queue's `next`) instead of building a `Store<OldG>`, because new code cannot name old types and old and new stores must coexist in one fixed arena. Any change to the `Store` wire shape must update `Store::write_canonical`/`decode` and `OldStore::decode` together or old saves silently misparse. The only statement is a doc comment in `migrate.rs`; `persist/CLAUDE.md` says "field order is fixed" without this second consumer. — source: docs/plan/24b-upgrade-and-migration.md:150 — proposed home: line in packages/engine/crates/engine/src/persist/CLAUDE.md
