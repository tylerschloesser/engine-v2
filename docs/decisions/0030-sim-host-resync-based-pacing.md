# 0030: `SimHost` pacing reads the wall clock only once every `RESYNC_TICKS` ticks

Status: Accepted (2026-09-21). Amends the pacing decision of [`docs/plan/13-sim-host-tick-loop.md`](../plan/13-sim-host-tick-loop.md) (`onFire`'s per-wake `due` computation, `runOneTickTimed`'s per-tick overrun bracket) and narrows what `tickOverruns`/`ticksDropped` mean there. Implemented in M13b (`docs/plan/13b-tick-timing-allocation.md`). §2 amended by [0032](0032-atomics-timer-bounds-external-wakes.md).

## Context

M13 built `SimHost`'s pacing (`docs/plan/13-sim-host-tick-loop.md`, Scope "Pacing") to read `services.clock.now()` around every tick: `runOneTickTimed` bracketed each tick with two reads to detect an individual overrun, and `onFire` read the clock once per wake to compute how many ticks were due, catching up to `MAX_CATCHUP_TICKS` and dropping the rest. `worker/atomics-timer.ts`'s `AtomicsTimer` (M13 steps 4-6) added a third and fourth read per wake, in `poll()`'s due-check and `timeoutMs()`'s own deadline subtraction, to schedule `Atomics.wait`.

At M14's gate, CI found `gc-sim`'s negative controls intermittently red (`docs/plan/13b-tick-timing-allocation.md`, opening note; 0006's amendment list). Attribution: `performance.now()` returns a fractional double, and V8 boxes a fresh `HeapNumber` for every such read whenever the calling code is running in the interpreter tier rather than optimized -- a fact true of any of the reads above, regardless of what the surrounding JS does with the result (confirmed by experiment: truncating the read with `Math.trunc()` did not help, because the box happens at the native call's return, before any JS-side arithmetic can act on it). The sim worker is a strict zero-GC isolate, budgeted at 8 B/frame ([0016](0016-zero-gc-definition.md) §1); the halving experiment in M13b's own investigation showed that even *one* such read costs ~11.92 B/tick, already over budget on its own. [0016](0016-zero-gc-definition.md) §1 is explicit that "a zero-allocation guarantee that holds only when V8 wins a compilation race is not a guarantee" -- so a fix that merely reduces how often the interpreter tier runs (a bigger warm-up, say) was rejected on principle, not just on measurement.

M13b's own Step 1 (arming `simHost.start()` for real on a new zero-GC page, `gc-sim-paced`, since no prior page ever exercised the production pacing path -- test topologies drive ticks deterministically through `CB_SIM_STEP_REQ` instead) found the defect was **not intermittent once real pacing runs at all**: `AtomicsTimer`'s own reads cost ~14.5 B/frame under default, unforced V8, before this ADR's fix.

**Three fix directions were measured** (forced interpreter tier, `--js-flags=--no-opt --no-sparkplug`, a diagnostic never left in the tree):

1. **Integer-only deadline arithmetic, read via `Atomics.load` on a plain `Int32Array`.** A bench loop performing the same comparisons `poll()`/`timeoutMs()` do, but keeping every value an integer (Smi-representable, never boxed): the bench function disappeared entirely from the isolate's allocation profile (`byFn`) -- zero attributed bytes, not merely fewer.
2. **Event-based on `Atomics.wait`'s own timeout**, no clock read at all: trivially zero allocation, since there is no call left to box. Rejected on correctness, not cost: waiting a constant period per tick means each cycle actually costs `period + the tick's own work time`, so (for example) a 20 Hz sim with 5 ms of per-tick work paces at roughly 18 Hz, and the error accumulates without bound for as long as the host runs. Any scheme that corrects for the tick's own work needs to measure it, which needs a clock, which is back to the same problem.
3. **A WASM-imported monotonic clock.** Built for real (a scratch Rust `cdylib` declaring `#[link(wasm_import_module = "engine")] fn now_ms() -> f64;`, called in a loop, `now_ms: () => performance.now()` supplied as the import) and measured: 7.98 B/tick under forced interpreter tier. The import's own JS-side glue closure is still an ordinary interpretable JS function, governed by the same optimizer-tier flags as any other JS -- crossing the WASM boundary does not exempt it. Rejected: it does not eliminate the allocation, and a number that close to the 8 B budget would leave no margin even had it passed.

## Decision

**1. `SimHost` reads the real clock only once every `RESYNC_TICKS` ticks, never per wake or per tick.** `RESYNC_TICKS = 8`, chosen by measurement: one `clock.now()` read costs ~11.92 B in the interpreter tier; the resync function's own read plus one more inside the chunk warmer's loop condition (~23.84 B total, the same order as the two-reads-per-tick figure this replaces) amortised over 8 ticks is 23.84 / 8 = 2.98 B/tick, with real margin under the strict 8 B/frame budget for the rest of the loop's own overhead (measured after building it: 2.92-3.00 B/tick, `resync@...` the only entry in the isolate's `byFn`, confirmed to disappear the same way under forced `--no-opt --no-sparkplug` too). At 20 Hz this is a 400 ms resync window.

**2. Between resyncs, every wake (armed `AtomicsTimer`) or every `stepTick()` call runs exactly one tick, unconditionally, with no clock read and no due-check.** `AtomicsTimer.poll()` no longer computes a deadline: `timeoutMs()` always answers the fixed, already-integer `ms` it was armed with (or `Infinity`, unarmed); `poll()` calls its callback on every wake while armed. `SimHost.onFire` and `SimHost.stepTick(n)` both call one shared function, `runPacedTick`, so a real single-player session and `stepSimTickSync`-driven zero-GC test coverage share one accounting path.

**3. Every `RESYNC_TICKS`th tick, `resync()` is the only place the real clock is read**, comparing the real elapsed time since the last resync against what those ticks were budgeted to cost (`ticksSinceSync * tickMs`, integer arithmetic throughout the window; the anchor itself, `syncBaseMs`, is `Math.floor`ed to an integer once per resync so nothing between resyncs ever holds a fractional double):
   - If the window ran long, `tickOverruns` is incremented **once per window**, not per tick. Which individual tick (if any) was actually slow is no longer identifiable -- this is the semantic narrowing this ADR records.
   - The real elapsed time is converted to a whole-tick count behind schedule (`behindTicks`); up to `MAX_CATCHUP_TICKS` (unchanged from M13: "the host runs at most 5 catch-up ticks per wakeup") are run synchronously, right there, to catch up for real; the remainder is dropped, incrementing `ticksDropped` by exactly that amount -- the identical cap M13 applied per wake, now evaluated once per 8-tick window.
   - The chunk warmer (`warm`, 0008 §2) is also called from `resync`, once per window instead of once per wake, budgeted the same `WARM_BUDGET_MS` it always was.

**4. The drift this introduces is bounded and self-correcting, not merely coarser.** Assuming every tick costs exactly `tickMs` (ignoring the tick's own real work time) is exactly candidate 2's assumption, but only *between* resyncs: at most `RESYNC_TICKS` ticks' worth of error (400 ms at 20 Hz) can accumulate before the next resync measures the real elapsed time and erases it, moving the schedule's own anchor forward by exactly what was accounted for. This is the trade this ADR accepts in exchange for eliminating the per-tick allocation: bounded, periodically-corrected imprecision in exchange for a guarantee that holds under any V8 tier, not only an optimized one.

**5. `start()`/`resume()` reset the resync anchor** (`syncInitialized = false`, `ticksSinceSync = 0`) instead of M13's `base += now - pausedAt` adjustment: the next tick after (re)arming sets a fresh anchor from real "now" at that moment, which makes a paused interval invisible to pacing (0005 "Idle pause is replay-safe") with less bookkeeping than before (`pausedAt` is gone entirely, nothing computes a duration from it any more).

**6. No ABI change.** Every read that moved is JS-side (`packages/engine/src/server.ts`, `worker/atomics-timer.ts`, `worker/sim.ts`, `worker/protocol.ts`); no export, import or `ABI_VERSION` is touched. `SimHostCounters`'s shape (`ticksRun`, `ticksDropped`, `tickOverruns`, `chunksWarmed`, `genOnMiss`) and `SimHost`'s public method signatures are unchanged.

## Alternatives rejected

- **Event-based on `Atomics.wait`'s own timeout** (candidate 2 above): unbounded pacing drift under any nonzero per-tick work time. Rejected on correctness.
- **A WASM-imported monotonic clock** (candidate 3 above): measured at 7.98 B/tick under forced interpreter tier; does not eliminate the allocation, since a WASM import's JS-side glue is still ordinary JS. Rejected on measurement.
- **A `SharedArrayBuffer` time source written by a non-strict isolate** (main thread), extending the "WASM reads times from its own region" pattern `worker/client.ts`'s `frame_time_ms` fix already uses for the camera block (`.claude/rules/hot-paths.md`). Considered during the investigation but not built: it has no natural periodic writer on a page with no render loop (every zero-GC page, and any backgrounded/paused-render single-player session), and would make the sim worker's own pacing depend on main being alive -- exactly the case `AtomicsTimer` (`Atomics.wait`-based blocking, not a `setInterval`) was built to keep working through.
- **A dedicated third thread whose only job is advancing a shared clock word.** Avoids the main-thread dependency above, at the cost of a new permanently-running worker per single-player session and its own zero-GC accounting surface (0016 §1 measures every isolate). Rejected as disproportionate to the problem: adding a thread and a topology to save one clock read.
- **Reducing read *frequency* without a periodic real resync** (e.g. only checking due-ness every few wakes, with no correction step). Rejected for the same reason as candidate 2: without ever comparing against the real clock, drift is unbounded.

## Consequences

- `tickOverruns` answers "did this ~400 ms window run long", not "which tick, if any, ran long". A consumer that needs per-tick attribution (a future profiling or diagnostics feature) needs a different, explicitly per-tick instrument; this counter no longer provides one.
- `ticksDropped`'s cap (`MAX_CATCHUP_TICKS`, unchanged at 5) is now evaluated once per `RESYNC_TICKS`-tick window rather than once per wake: a host that falls behind by more than `MAX_CATCHUP_TICKS` ticks *within* a single window still only catches up 5 and drops the rest at that window's resync, the same shape as before, just on a coarser clock.
- `RESYNC_TICKS` is chosen for the 20 Hz default tick rate `fx-puts` uses; a much faster configured `Game::TICK_RATE` (up to 60 Hz, [0010](0010-rates-and-subscriptions.md)) shortens the wall-clock resync window (400 ms at 20 Hz, 133 ms at 60 Hz) but does not change the per-tick byte math (`RESYNC_TICKS` amortises a fixed per-resync cost over a fixed tick count, independent of `tickMs`). Not re-measured at 60 Hz; flagged for whoever first ships a non-default tick rate.
- Deferred: whether a future milestone wiring a real external wake into the sim worker (M15/M16 connections/actions -- Non-scope of M13b) needs `AtomicsTimer` to distinguish a genuine timeout wake from an external one. Nothing today wakes a production sim worker except its own timer, so `poll()` firing unconditionally on every wake is correct as built; the day something else legitimately wakes it (an incoming action, say), firing an extra unwanted tick on that wake becomes possible and this file's own `poll()` will need revisiting.
