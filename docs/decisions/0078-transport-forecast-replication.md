# 0078: Replicating transport lines: structures as puts, motion as forecasts with corrections

Status: Accepted (2026-10-11, as revised by the Amendment below: §2 and §3 are amended, A3; §5's gated cell is fixed, A5). A3's rules 4 and 6, its spawner schedule and §7's one-second rule are amended by A8 (milestone 47, 2026-10-12). A5's gate is measured live and A6 (i) left unbuilt by A9 (milestone 47b, 2026-10-12). The Consequences' late-join criterion is measured and not met on the fixture world by A10 (milestone 48b, 2026-10-12): the levers are duplicate lists and the fixture's spawner deltas, not the structure encoding. Implements [0076](0076-transport-lines-engine-game-split.md) §7; amends [0011](0011-wire-format-and-deltas.md) (two new sections), [0013](0013-sessions-and-integrity.md) (what the per-chunk hash covers) and [0012](0012-prediction-and-reconciliation.md) "Remote motion" (a second interpolation path beside `InterpBuffer`). Measured in milestone 41 (`docs/plan/41-forecast-spike.md`), built in milestones 46-48.

## Context

A client must draw items moving at 60 fps on belts that span far beyond its viewport, while the host sends nothing per tick that merely says "everything moved by one step" (`docs/architecture/sync-and-netcode.md`: never replicate per-tick progress) and the client runs no belt logic (Tyler, 2026-10-11). Tyler's answer is forecasting: for each visible item or run the host says where it will be, and sends an update only when the forecast turns out wrong. Exact motion depends on upstream and downstream state that is too costly to walk every tick, so the forecast is deliberately cheap and its corrections are budgeted. The replication budget is the existing soft cap of 16 KB/s per client (`host/pacing.rs`), with every visible belt saturated.

What exists: chunk-scoped whole-value deltas with versions ([0011](0011-wire-format-and-deltas.md), [0064](0064-phase-3-decisions-sync-and-netcode.md) §18), chunk snapshots on subscribe, per-chunk desync hashes ([0013](0013-sessions-and-integrity.md)), a client render time `host_now - delay` with the delay sized from the presence interval ([0040](0040-interpolation-delay-presence-interval.md): floor 200 ms, cap 400 ms), and `InterpBuffer` for presence and "moving entities" that no game has yet ([0012](0012-prediction-and-reconciliation.md)).

The observation the scheme rests on: the client renders tick `t` only after `delay` (at least 200 ms, four ticks) has passed on the host clock. A correction the host sends at tick `t` reaches the client after one-way latency, which on the target networks (`docs/architecture/README.md`: decent mobile, not worst case) is under the delay. So a correction usually arrives *before* the client renders the tick it corrects, and the forecast is wrong on screen only when latency exceeds the delay or a frame is lost. The forecast is not a prediction of the far future; it is what lets the host stay silent while things go as expected.

## Decision

**1. Two kinds of replicated line data.** A line's **structure** (`len`, `speed`, `Output`, segments, anchor chunk; [0076](0076-transport-lines-engine-game-split.md) §4) is replicated whole-value per line, on change, like an entity: a new frame section `LineStructs` (section id 12; `wire/CLAUDE.md` owns the layout) carries `Put { id, structure }` and `Gone { id }`, routed to every connection whose subscription meets the line's chunk set; a `ChunkSnapshots` entry also carries the structures *anchored* in that chunk (anchor = the chunk of the line's front point, the multi-tile entity rule of [0007](0007-world-model.md) §5), with their forecast at the snapshot tick. A line's **motion** is replicated as a **forecast** through section `Forecasts` (13).

**2. A forecast is per line, at a tick `T`, and lists runs.** `Forecast { line, tick: T, runs: [RunForecast] }` with `RunForecast { item, count, pos: position of the first item at T, stop: Option<position>, path: [LineId; <= 4] }`:

- A run moves toward the front at the line's speed: `pos(t) = max(pos - speed * (t - T), stop)` for `t >= T`; items in a run are `SPACING` apart behind the first.
- `stop` is where the first item will halt (the end of a jam ahead plus `SPACING`, the line front of a `DeadEnd`, the front of a blocked `Merge`/`Fork`), or `None` when nothing in sight blocks it.
- When `pos(t)` goes below 0 the run continues at `pos + next.len` on the next line of `path`; past the explicit `path` it follows `Output::Next` links as long as they are plain (`Next`) and stops at the front of anything else. A run that will split at a `Fork` is sent as several entries (one per contiguous group with the same path), so a path is always one line per entry and the client makes no choice. A `Merge` target in `path` carries its landing position explicitly (`enter_pos`, the host's `at - overshoot`), so the client applies no entry rule.
- The client stores the latest forecast per line and evaluates it at its render time (host ticks, fractional, from `InterpDelay::render_time`) with linear motion, no squash and no rule. That is the whole of client interpolation for items: "follow the forecast". `InterpBuffer` is not used (items do not carry velocity samples; their motion is piecewise linear by construction).

**3. The host sends a line's forecast when it changes, and otherwise never.** `Transport::advance` computes each line's new state anyway; it marks a line *dirty* when the tick's outcome is not what the current forecast says: a run blocked at a position other than its `stop`, a run that moved although its `stop` said it would not, a hand-off or fork decision other than the forecast's path, an item inserted or removed (spawner, sink, inserter, surgery), a structure change. A clean tick marks nothing. The per-tick cost of this check is one comparison per run that was touched by the advance, which a run representation keeps near O(lines that changed) ([0077](0077-transport-item-representation.md)). After the advance the host rebuilds the forecast of each dirty line (the *cheap* forecast: what the line will do if its upstream inputs and downstream outputs keep their present state; it walks at most the `path` depth of 4 lines) and queues it to every connection whose subscription meets the line's chunk set. Nothing is sent for a line whose forecast did not change, however long it keeps moving.

**4. Scope and culling.** A connection receives a line's structure and forecasts while any chunk of the line's set is subscribed; it receives `Gone` for the structure when it drops out (chunk leave) and forgets the forecast with it. Runs outside the subscribed chunks are not culled in the first build (a merged line is sent whole); milestone 47 measures the bytes at the stated scale and adds a position-window cull (`runs whose positions map into subscribed chunks`) only if the budget needs it.

**5. Budget.** `counters.transport.downBytesPerSec` in `budgets.json`, ceiling 16,384 B/s per client measured in the netcode harness on the saturated-viewport scenario of milestone 47 (a dense grid of belts and splitters fed by spawners into sinks, with jams forming and clearing at a stated rate), with production hashing on and the client's whole view subscribed. The measurement also records `transport.correctionsPerSec` and corrections per visible run per second; the amendment that accepts this ADR states both. A `forecast_seen_late` client counter (a correction applied for a tick the client has already rendered) measures how often the screen was wrong; it is reported, not budgeted, in this effort.

**6. Hashes and prediction.** The per-chunk desync hash covers line structures anchored in the chunk and nothing of the items: the replica's items are forecast-derived, never authoritative per tick, and must not be compared. The full state hash and snapshots cover everything ([0076](0076-transport-lines-engine-game-split.md) §7). Under prediction there are no transport writes ([0076](0076-transport-lines-engine-game-split.md) §6); the client's overlay never touches a line.

**7. Degrade and overflow.** A connection degraded to every 2nd or 4th tick ([0010](0010-rates-and-subscriptions.md)) receives the latest forecast of each dirty line in the frame it gets; forecasts are idempotent whole values, so skipped frames lose nothing. A frame that cannot fit every dirty forecast keeps the rest dirty for the next frame (the same rule as queued chunk deltas), and a line whose queued forecast is older than one second is resent in full on the next frame regardless.

## Alternatives rejected

- **Replicate item positions every tick for visible lines.** Per-tick progress on the wire; at a saturated viewport it is hundreds of kilobytes per second.
- **Client-side belt simulation of the visible lines.** Tyler's rule, and [0012](0012-prediction-and-reconciliation.md)'s reason: inputs from unsubscribed lines make it systematically wrong.
- **Forecast per item, not per run.** Bytes scale with items; runs are the natural unit (packed items share one future) and are what [0077](0077-transport-item-representation.md) stores.
- **A fixed horizon with periodic refresh.** A refresh every `H` ticks for every visible run is a steady cost proportional to visible items (about 15 KB/s at 1,500 visible runs and `H = 16`), the opposite of "send only when wrong". A forecast is valid until invalidated; `path` plus "follow plain `Next` links" keeps a free-flowing run valid for as long as it flows.
- **Hermite through `InterpBuffer`.** Items have no sampled velocity; their motion is exactly linear between hand-offs and stops.
- **Hashing items in the chunk hash with a tolerance.** A hash cannot be tolerant; structure-only is exact and cheap.

## Consequences

- New wire sections 12 and 13, new `wire/forecast.rs` writer and reader, both allocation-free; `no_alloc_wire` extends to them.
- The host keeps per line a `forecast_version` and per connection a `last_sent` map (a sorted `Vec`, reserved at attach for `max_lines`), plus a per-tick dirty list; all preallocated.
- The late-join cost at scale (every structure and forecast of a dense world through the 48 KB/s chunk bucket) is measured in milestone 48 and may need a smaller default view or a compact structure encoding; recorded, not solved here. Measured in milestone 48b (A10): 18.85 s and 2.9 MB on the fixture world, structures 3 % of it; milestone 48c dedupes the list a snapshot re-sends and re-measures with stateless feeders; the 10 s criterion is judged on the reference world in milestone 57.
- Deferred: forecasting a spawner's periodic inserts (a `period` field on a line, so a spawner at a steady rate causes no corrections); position-window culling (§4); any smoothing of a late correction on screen (today it snaps; `forecast_seen_late` says how often).
- A8 (milestone 47): a run list carries stops and replaces the whole line; an arrival carries its stop; a held line's deferred update goes `Gone` and is put again; lists larger than a frame are `unknown`; a mixed-speed junction costs a list a tick until a speed-override state exists.
- A9 (milestone 47b): the gated cell reads 3,958 B/s and the stress cell 19,468 (A4 modelled 4,947 and 24,736); puts are two thirds of the bytes; the bytes scenarios lift chunk pacing because the fixture's spawner entities write a delta per insert, so sections 12 and 13 under degrade or collapse wait for milestone 48's late-join and degrade measurements.
- Trigger to revisit: `transport.downBytesPerSec` over budget in milestone 47 with the cheap forecast, or `forecast_seen_late` above 1 % of rendered ticks on the median network.

## Amendment (2026-10-11, milestone 41): the measurement, and the scheme as revised by it

**A1. What was measured.** The native spike of milestone 41 (`packages/engine/fixtures/belts/tests/spike_forecast.rs`, on milestone 40's winning store; its Deviations hold every table) instrumented the dirty events of §3 inside the advance, rebuilt the cheap forecast of §2 for each dirty visible line, and modelled its bytes (`4` line + `4` tick + `1` count, per run `2 + 1 + 3 + 3 + 1` plus `3` per path line; deliberately generous) at 20 Hz, 200 warm-up and 1,200 measured ticks, on two worlds: the mixed world of milestone 40 seen through a 256 x 144 viewport (1,010 visible lines, 43,749 runs) and a `SaturatedView` world (the whole viewport belts: 144 rows, 982 lane chains, 2,974 lines, 36,864 tiles, 294,912 items, every lane fed to saturation and draining into a sink) with a fraction of the sinks toggled closed and open on a staggered schedule: `(jam %, period ticks)` = (0, -), (5, 100), (20, 100), (20, 20).

**A2. §3 as written is two orders of magnitude over budget, for a reason the ADR did not see.** Counting every insert and every sink exit as a correction, the jam-free saturated viewport costs 7.8 to 9.0 MB/s: 368 corrections per tick, exactly one insert and one exit per lane per 2.67 ticks, each resending a whole line. Both fixes the Consequences deferred are therefore adopted: a sink exit is predicted by the path's terminal `Sink` (not a correction), and a forecast carries the spawner's schedule (`rate256`, accumulator), so an insert at the steady rate is not a correction. With both, the jam-free cell costs 0 B/s and the mixed viewport 1.2 KB/s. The jam cells stayed over (892 KB/s at (20, 20)) because a jam forming or clearing halts or releases every line of a packed chain in one tick, and each line resent its whole run list (about 1.3 KB for a lane of alternating kinds) although not one run had changed.

**A3. The scheme, revised (amends §2 and §3).** A line's forecast is two things, sent separately:
- *The run list*, `[RunForecast { item, count, pos }]` at tick `T` (positions of first items; items in a run `SPACING` apart), sent in full only when membership changes in a way the client cannot derive: an inserter's or surgery's insert or remove, an off-path hand-off (a `Fork`), a late join or a structure `Put` of a line the client has not seen. Spawner inserts and sink exits are derived (A2); hand-offs along the path are covered by the ownership rule below.
- *The motion state*: `front_stop: Option<cumulative position>` (where the line's front item at `T - 1` halts; cumulative along the path in the line's coordinates, negative on a downstream line) and the spawner's schedule (`rate256`, accumulator, cycling flag and next item: 7 B in a full list) with its `paused` flag. The client's replay of that schedule (an item at the back every period, landing at its own tail) is the one place the client computes a landing; it is recorded as **(assumed)** in `games/reference/README.md` "Belts" until Tyler rules whether it counts as following the forecast. Every run's stop derives from it: item `k` of the line (counted from the front) halts at `front_stop + SPACING x k`. A **state message** (`line`, `front_stop`, flags; the tick is the frame's) is the correction for a halt, a release, a change of the stop ahead, a jam reaching a spawner and the spawner resuming, and a structure change (whose structure travels as its own `LineStructs` put, §1). The client evaluates the line's items at `T - 1` from what it holds, then applies the new stops with §2's formula. A client that knows only this (the formula, `Next` following, the ownership rule, the message rules below and the spawner replay) matched the advance's positions and item counts on every visible line on every one of 300 ticks over seven worlds, including an inserter-edited one, a `speed = 72` one, a viewport that cuts chains and a world that starts empty (`forecast_client_matches_advance`, the arbiter the adversarial review asked for; its first version had three cases where the host's stops and the client's reconstruction differed, each caught by this test and closed by the rules below).
- *Message rules* (milestone 47 implements them as written): (1) a message of line `L` at tick `T` covers the items `L` held at `T - 1`, including those that crossed its front during `T`, plus the items inserted on `L` during `T`; never the items that landed on `L` during `T`. (2) An item in two lists (it crossed from `S` to `L` during `T`) belongs to `S`: `S`'s message re-stops it, `L`'s never touches it; the host keeps such landers as their own segments with their own due tick. (3) A state message's `front_stop` is the stop of the first item of that list, `s0 - SPACING x crossers`. (4) A full run list replaces exactly that list: crossers at their negative positions, inserts included, landers excluded; never "the items the client places on `L` at `T`". (5) An insert onto an empty line gets no stop, on both sides. (6) An item arriving on a visible line from a line the client does not hold is sent as `Arrival { line, item, pos }` (9 B modelled) with a stop `SPACING` behind the line's last item at `T - 1`, or none if it held none: 4.7 arrivals per tick, 843 B/s, for the mixed world seen through a 64-tile-wide viewport (112 KB/s if each were a full run list), so arrivals are a per-connection correction milestone 47 must send.
- *Ownership* (a gap in §2): a forecast describes the items on its line at `T` and keeps describing an item after it crosses into a downstream line until that line's own forecast is rebuilt; a newer forecast of a line replaces only the items still on it. Without this, rebuilding a line orphans the items it handed off.
- *The cheap forecast's horizon*: the host walks the path to the first jam, dead end or sink, at most 8 lines (not 4): at depth 4 one line per tick at (20, 20) had a blocked item whose front stop lay beyond the horizon and needed a full resend; at depth 8 none did, in every cell. A line at the horizon whose front item held still this tick counts as a jam.
- *Detection cost*: the host checks the line's front item per tick (if it moves as predicted every packed item behind it does) plus a "due tick" per landed item whose stop is not the chain ahead; one comparison per hand-off, O(dirty) rebuilds. Measured on the chosen configuration (state messages, depth 8): +57 µs on the mixed world's 19 µs tick and +49 µs on the saturated viewport's 20 µs tick; the §3-as-written configuration cost +249 µs, half of it an end-of-tick scan over every line that a due-ordered queue removes (milestone 47 if milestone 45's baseline needs it). The spike's `path` field is unnecessary once structures replicate (§1): the client follows `Next` links it holds; a path entry is needed only where a `Fork` decides.

**A5. Budget (amends §5).** `counters.transport.downBytesPerSec` covers sections 12 and 13 together, ceiling 16,384 B/s, gated on the saturated-viewport scenario at (20 %, 100) in milestone 47 (modelled 4,947 B/s, so the row can trip on a 3x regression and on any return to whole-line resends). The (20 %, 20) cell is measured by the same scenario and recorded in the row's formula, not gated; if milestone 47 reads it above 32,768 B/s (twice the soft cap, where degrade to every second tick begins to hide it), the chain-level lever below is built. `transport.correctionsPerSec` and `forecast_seen_late` are recorded as §5 says.

**A6. Deferred and levers, in order.** (0) Arrivals from unheld lines are per-connection corrections (A3 rule 6): the host's dirty tracking is per line, the arrival check per connection; sized by milestone 47. (i) A chain-level halt: one message per chain instead of one per line, the client deriving each upstream line's stop from the downstream line's rear (a derivation from forecast data the client holds, not a belt rule; not built until needed). (ii) Position-window culling (§4): not needed by these numbers; the whole-viewport world is the worst case and is under. (iii) The client keeps every visible line's run list (memory, not bytes): sized in milestone 47. (iv) `path` only at `Fork` crossings.

**A8. The scheme as built (2026-10-12, milestone 47; amends A3 rules 4 and 6, A3's `rate256` schedule and §7's one-second rule).** The engine half (`transport/forecast.rs`, `transport/follow.rs`, `wire/forecast.rs`, `host/lines.rs`; `docs/plan/47-forecasts-and-corrections.md` Deviations hold the evidence) kept A3's rules 1-3 and 5, the ownership rule and the depth-8 horizon as written, and changed what the arbiter forced (`forecast_client_matches_host`: eight hand worlds, two views, five frame sizes, exact `items_in` on every held line every tick and every line in view held at the end):
- *A `RunList` carries a stop per run and means the line's whole list at `T`* (rule 4 said: the `T - 1` list, landers excluded). A list without stops cannot say what a `State` cannot (the classifier's reason to send one), and a list that replaced only the `T - 1` items left the client stepping a line it was being told was wrong, feeding its crossers on into lines it holds. The client empties the line before it steps `T` and takes the list after; the replaced line's crossers that tick reach their targets as arrivals.
- *An `Arrival` carries its stop* (rule 6 derived it `SPACING` behind the target's last `T - 1` item). A `Merge` lands mid-line, where that chain is wrong; and with several connections one may hold the source (following the item with the source's stop, rule 2) while another holds only the target: one model for every connection needs the stop on the wire (+4 B). Arrivals also carry a `Fork` crossing (the client never decides a fork: no `fork_side`), a hand-off from a line resent that tick, and an `insert_back` on a line with no declared spawner; a `Merge` landing resends its target's list (every item behind it stops one item further back). So a side-load costs a list per merged item and a splitter an arrival per item: a measured cost, not a limit; A6's levers (mid-line arrivals with a due segment, a client-side toggle replay) wait for milestone 47b's bytes and milestone 52's belts.
- *The spawner schedule is the declaring game's period rule* (`period`, `acc`, `kinds`, `next`; each tick `acc += 256`, an attempt at `acc >= period`, success `-= period`, refusal `-= 256`), not `rate256`: a host must declare exactly what it runs. The client's replay attempts each insert by `insert_back`'s landing rule against the tail it holds, so a refusal for room is predicted; only a refusal it cannot see (the item cap) pauses the schedule, by a `State` flag. A declaration is derived state (`set_spawner` returns nothing a sim may branch on; one the tracker cannot hold is counted), lost on restore: milestone 48 builds the re-declaration.
- *Nothing is left dirty on a client, so §7's one-second rule has no timer.* `State`s and `Arrival`s are unbudgeted (a few bytes each, like `Gone`); a put of a line the client did not hold carries its list and is priced with it; a held line whose correction or structure update does not fit the frame's put budget (0079 §17 (c)) is sent `Gone` and put again later with its list, so no client steps a model the host no longer holds (0079 §18 (b)). A frame that overflows loses its records, and the next frame sends `Gone` for the lines it changed or named (every held line with a put, a `Gone`, a deferred update, a message or a record that tick) and one level of targets (their held hand-off targets that tick, their current `Next` targets, and the old targets of `Next` outputs changed or destroyed that tick, from a per-tick log of `max_lines / 4` entries whose overflow loses every held line), never for every held line otherwise: the review's first form did, and a connection overflowing more often than its re-put took never held its view; its second form forgot the lines whose budget `Gone` the lost frame carried. One level suffices because the client steps a skipped tick before the next frame changes anything: `on_frame` catches the follower up to `T - 1` under the structures and stops it holds before frame `T`'s first section (the review found the first order, catch-up after the puts, losing every crosser of a quiet tick that preceded a structure change; the arbiter's per-tick catch-up is that same call). A line whose put and list exceed an *empty* frame's put budget is put with a list flagged `unknown` (the structure held, so chunk hashes agree; no items on the client until the list fits, sent then as a budgeted correction; the client refuses a landing onto it and the host sends an `Arrival` for each crossing out of it; `listsUnknown` counts it); after an overflow the first put, correction or recovery is admitted within the halved budget, so a list between the halved and the full bound waits rather than overflowing again, and every path judges `unknown` on the same sum (structure plus list) so a line never alternates; `pos_at` stops where the step would (an item whose path reaches an unknown line vanishes); `State`s and `Arrival`s stay unbudgeted and a list between the halved and the full bound can wait while frames alternate between lost and sent: both bounded, measured by milestone 47b: without the bound, the first-put-always-fits rule stalled a connection for good on one list larger than a frame (16,384 items of alternating kinds on a 4,096-tile line is about 196 KB against a 64 KiB frame).
- *Structure changes*: `set_out` and `set_speed` are `State`-eligible (a sink toggle is a `State`, as A4's cells need), except a speed change on a line with a declared spawner after that tick's insert (the replay would land by the new speed: resent); create, surgery, redirects and `set_segments` resend the list, as do a squashed line, a cut landing that still moves and a full segment pool. A change of the stop ahead is found lazily, at the first deviation it causes (the front check or a due tick), never propagated upstream.
- *Pricing*: a list's bytes are priced by a bound never below the bytes written (`runs + segments - 1` runs plus one per lander the segment pool refused, O(segments)), not counted: counting exactly for every chunk the delta-collapse estimate prices each tick cost 18 % of the bench's samples.
- *Known limit, measured not fixed*: a fast line feeding a slower one has its front blocked behind a moving tail every tick, which a model of stops cannot say, so such a junction costs about one list a tick (the eighth arbiter world: 72 into 24 into a sink, exact, 0.9 lists and 0.3 arrivals a tick). The reference game runs one speed; the lever is a `State` with a speed override, for the first game that needs it.
Memory (0079 §5's rule, reserved at `set_transport_caps` by role): the host's tracker is 104 B a line and 4 B an item, the replica's follower 48 B a line and 16 B an item (and a replica reserves no run nodes, update order, Tarjan scratch or change list); at the recommended caps a host reserves 21,168,160 B and a replica 17,498,128 B (was 16,646,160 for both, 0079 §17), and the phone pair of milestone 45 moves from (16,384, 131,072) to (12,288, 98,304) lines and items, 7,979,040 B on the host and 6,602,768 B on the replica, sized by the larger role (A6 (iii) sized). Bytes: `State` 3 B (7 with a stop), `Arrival` 9 B (13 with a stop), `RunList` 4 B + 12 B a run (+7-15 B of spawner); `wire/CLAUDE.md` holds the layout; the counters ride their own export (`client_forecast_counters`, ABI 42; `forecastCounters(client)` in `engine/test`). `pos_at` before the forecast tick extrapolates back along the line (milestone 49 settles it with history). Milestone 47b measures the cells of A4 on the wire and gates A5's row.
