# 0063: Phase 3 decisions: world and simulation

Status: Accepted (2026-10-10). Records decisions Phase 3 made that no ADR holds, so the plan files that carried them can be deleted. Settles the two deferred items of [0007](0007-world-model.md) (overlay promotion, area effects) and the deferred item of [0008](0008-chunk-generation.md) (sampled pristine-hash check); amends [0007](0007-world-model.md) §6 (overlap) and [0030](0030-sim-host-resync-based-pacing.md) (one caveat). Implemented across M05 to M39ai.

## Context

Phase 3 built the world and simulation layers against ADRs that still list several items as "deferred to Phase 2/3", and made choices in milestone briefs whose reasons would otherwise be lost: why the codec is shaped as it is, why overlap is not an engine error, why the large-save tick is slow on phones, which optimisations were tried. Each entry below is the decision plus the reason that prevents re-litigating it.

## Decision

### World

**1. Overlay promotion and area effects are not built (settles 0007 deferred).** Promotion of a chunk overlay to a dense chunk at 512 entries is not built: reads never consult the overlay, a sorted insert moves at most a few KB, and the 12 MiB overlay share already prices the worst case. It is a pure representation change behind `ChunkOverlay` (canonical bytes stay the sorted entry list), so it needs no ADR when added. Trigger: the standard-large-save run shows overlay memory, not entities, breaking the world budget, or a game appears whose rules rewrite whole chunks. Bucketed per-chunk area effects are also out: no reference rule is area-based and chunks do not tick ([0007](0007-world-model.md) §7); a game that wants them brings an ADR, naturally beside the active lists.

**2. No sampled pristine-hash check between client and server (settles 0008 deferred).** Under one `.wasm` plus the handshake build hash, a divergence is an engine or JIT bug, and three cheaper nets exist: the six-runtime worldgen golden, the fingerprint in saves ([0007](0007-world-model.md) §9), and `insert_pristine`'s debug assertion comparing gen-worker output with the instance's own generation. If a field report ever needs the check, it is one more entry kind in the `Hashes` section beside the per-chunk hashes, so that entry-kind byte must stay extensible.

**3. Overlap is not rejected by the engine (amends 0007 §6).** There is no debug panic on a put whose footprint covers a tile another entity occupies. `ChunkIndex` is overlap-tolerant (`entity_at` answers the lowest id, `overlapping()` lists every id, `entities_in` sees both) and `Registry::prototype_traits`/`footprint` are total (an unregistered id has empty traits and a 1x1 footprint). The assert was built and removed in M21: about a dozen pre-existing test `Game`s use a fixed `anchor`/`PrototypeId(0)` stub and panicked on the second spawn, and a test is never weakened to suit a new assert. Real games prevent overlap with the "ask the tiles" convention (`can_place` via `traits_at`, plus a game-side overlap guard test). A future "add the missing overlap assert" would re-break that fleet; if wanted, restrict it to registered prototypes.

**4. Cache event recording is opt-in.** `TerrainStore::enable_cache_events` turns on `Cache::events` and is called only where a store is paired with an `Uploader`, because the host path never drains events and the queue grew without bound. Rejected: a `TerrainStore::new` signature change, a `TerrainFeed`, and self-enabling on the first drain (it would silently miss earlier events). `GenQueue` therefore reads a separate always-on scalar (`cache_invalidation_seq`) instead of draining events: a second drainer inside `frame()` would starve `Uploader::on_frame`'s `changed` flag.

**5. `replace_overlay` re-materializes a resident chunk synchronously (known limit).** Evict-then-async showed a one-frame non-resident chunk. Measured only with fixture worldgens (198 to 781 ns per chunk); a real worldgen near `worldgenMsPerChunkWarn` (0.25 ms) would cost about 32 ms in one frame on a 128-chunk join burst. Fix if that happens: spread the re-materialization over frames, but never write `INDIR_NONE` in between.

**6. A furnace covers a resource by trait, not by stored state.** Resources are `COLLECTABLE` only, and a furnace can be placed over one. Covering is derived: trait `COVERS_RESOURCE` (`1 << 2`) on the furnace prototype, and a tile is covered whatever `traits_at` reports through its occupant term. That stays right after load, after pick-up and in the predicted path with no bookkeeping and no encoded-state change. A collect in flight when a furnace lands ends with no item and no depletion; `StartCollect` on a covered tile gets `RefReject::NoResource`. Rejected: a stored flag (state, encoding and prediction cost). Tyler's answer (M39ai) chose this.

### Simulation

**7. Codec: canonical floats by a delegating `Serializer`, decoding policed by re-encode.** Canonical floats come from a delegating serde `Serializer` wrapper (`CanonSerializer`), not float newtypes and not a postcard `Flavor` (a flavor sees bytes, not types). Decoding is deliberately not wrapped (a delegating `Deserializer` must wrap every `Visitor`, several times the code). Untrusted bytes go through `decode_canonical`, which decodes, re-encodes non-strict and rejects any difference. The re-encode is load-bearing: postcard does not police canonicality itself (it accepts overlong varints such as `[0x80, 0x00]`). It is non-strict because untrusted bytes can legitimately decode to NaN, which must be an ordinary `NonCanonical` error, not a debug-assert crash. The state hash is the same canonical writer fed to an `Fnv64` sink instead of a `SliceSink`, so "hash = FNV-1a over canonical snapshot bytes" holds by construction. `usize` cannot be policed by serde (it arrives as `u64`), so it stays a review rule plus a source scan (see `.claude/rules/determinism.md`).

**8. `puts_idle_100` golden is never re-blessed; connected scenario has its own golden.** `puts_idle_100` is `.wasm`-authoritative and read by the native Rust test from the same file, so it is the repo's one continuous native-vs-wasm equality check; re-blessing it would delete that evidence. The connected scenario lives in a separate `golden-connected.json`. Adding a golden is allowed; changing an existing one is the orchestrator's call. The sim worker accepts a connection only when the SAB set it boots with carries a client link (`host.connect`, a topology fact), never via a test flag.

**9. Caveat to 0030: `resync()` corrects only in one direction (amends 0030).** [0030](0030-sim-host-resync-based-pacing.md)'s "bounded at one window and self-correcting" holds only when the sim is behind: `resync()` acts on `overshoot > 0` (`server.ts`) and has no branch for running ahead, so anything that made `poll()` fire faster than the tick rate would run the sim fast, uncorrected. Not reachable today (the measured error is the other way: external wakes suppress polls). Revisit if a new wake source is added.

**10. The tick benchmark's 3 ms desktop proxy is met by 4 %, by a short-circuit.** First measurement was 9.6 ms, 62 % of it in `encode_chunk_snapshot`, called from `Host::build_frame`'s collapse check per delta-bearing chunk per connection per tick only to compare against `pending`, which is nearly always under `MIN_COLLAPSE_BYTES`. The behaviour-preserving fix skips the encode when `pending <= MIN_COLLAPSE_BYTES` (64) and computes a chunk's snapshot size once per tick for all connections: 2.876 ms. What remains is per-delta-per-connection frame assembly (242 puts per connection per tick). Do not re-add a per-connection snapshot encode. Baselines were recorded after the fix, so the gate passes only because the median is under 3 ms: an engine change near `build_frame` can turn it red with no real regression. The Node twin has no absolute budget by design ([0024](0024-planning-amendments.md) §14). The per-tick cache is a sorted `Vec` with binary search because a `HashMap` violates clippy `disallowed-types` ([0002](0002-determinism-same-wasm-everywhere.md) §2).

**11. The large-save tick on phones is cold-wake cost, not wasm cost.** On the Pixel 5 and iPhone 12 the large-save tick costs about 3x the native tick. Measured (M39y): the same release bench `.wasm` in Node ticks at 1.7 ms back to back (1.3x native 1.3 ms) and 3.65 ms with a 50 ms sleep between ticks (Chromium 4.19), every phase slowing 2 to 3x together with the browser's p95/p50 shape. The cause is a core and caches gone cold in the idle gap (clock, L1/L2, TLB), the same mechanism as the Pixel's little-core wake; it is not wasm, Chromium tiering or the allocator (native and wasm share the root `[profile.release]`; only the allocator differs). Do not chase a wasm-specific fix. This is the evidence behind [0056](0056-ios-pacing-and-tick-bar.md) §3.

**12. The large-save tail is not engine work.** Natively the per-tick cost is flat (p50 1.258 ms, p95 1.407 ms, ratio 1.12; mean by `tick mod 2..64` flat). Timers are a `BTreeMap<Tick, Vec<EntityId>>`, not a hierarchical wheel, so there is no cascade, and nothing is periodic or phase-locked to the 100-tick furnace cycle. The Pixel's bimodal ticks (fast mode 7.5 ms, slow mode 21 ms, 17 % of ticks, mostly isolated) and the desktop's wide body (2 to 5.5 ms) are OS scheduling, which a page cannot control.

**13. Where the large-save pass time goes.** On desktop `sim_tick` is about 90 % of the whole sim-worker pass. Cost per furnace is flat (17 to 18 ns) from 1/16 to full scale: compute bound, not cache bound. Seal and resync are noise (under 0.1 ms). Frame build follows the view, not the save (0.4 to 0.65 ms); the native profile's 57 % "frames" was for 8 connections. The phone gap between pass p50 and `sim_tick` p50 (about 1.3 ms) is frame build. Follow-up work therefore targets the furnace tick, not `build_frame`. (Frame size at maximum zoom-out is about 35.5 KB per tick because the soft-cap collapse, `pending > snapshot_len`, re-snapshots the dense chunks; that is why frame build is 29 % of the desktop pass.)

**14. Optimisations for the 10 ms bar: built, tried and dropped, not built (M39y, M39ae, M39ag).**
- Built: timer buckets as `VecDeque` (the old `Vec::remove(0)` moved about 13 MB of ids per tick, about 10 % of the median); a dense `by_entity` table capped at `DENSE_LIMIT` (2^20 ids) because ids come from an untrusted snapshot (paced p50 down to 78.9 %); per-chunk entity iteration and snapshot caching in the frame path (whole-pass p50 down to about 87 %).
- Tried and dropped: an id-indexed table for `upsert_entity_op` gave no measurable gain (build p50 0.625 ms vs 0.625 ms) and, because it grows with the largest entity id, pushed `host_and_client_panning_allocates_per_new_chunk_not_per_tick` over its ceiling (89.49 B vs 88).
- Not built, the room left if a phone is short: `chunk_versions.insert` dedupe; a `put_entity` write path (each furnace is put once per tick, so "already recorded this tick" skips nothing); moving the entity table (`BTreeMap<EntityId, Entity>`, `store/mod.rs`, a quarter of native tick samples) off a BTreeMap, which is a storage change needing a decision; dedupe of the double encode of the collapsed chunk across ticks.

## Alternatives rejected

- **Float newtypes, a postcard `Flavor`, a wrapping `Deserializer`** (7): each is more code or sees the wrong layer for no extra guarantee.
- **A stored "covered" flag on resources** (6): state, encoding and prediction cost.
- **An engine overlap assert** (3): breaks the existing fixture games.
- **Self-enabling cache events on first drain** (4): silently drops earlier events.

## Consequences

- Items 1, 2 and 5 are deferred with explicit triggers: a large-save run where overlay memory breaks the world budget; a field report of client/server pristine divergence; a real worldgen near 0.25 ms per chunk.
- Item 10's margin is thin; a red tick benchmark after a `build_frame` change needs the profile first.
- Item 14's "not built" list is the first place to look if the iPhone 12 misses the 10 ms bar.
