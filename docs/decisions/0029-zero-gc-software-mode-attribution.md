# 0029: Zero-GC software mode: attribution stays on `main` only, and for a different reason than 0016 gave it

Status: Accepted (2026-09-21). Amends [0016](0016-zero-gc-definition.md) §3 caveat b. Implemented in milestone M10.

## Context

M10 turned on `GC_MODE=software` in CI for the first time, which ran 0016 caveat b's attribution mechanism (`attributedBytes`, keyed by `attributionRoots`) for the first time ever, on any isolate. It did not work.

**The finding that started it.** `GC_MODE=software pnpm gc software -t "gc-loop neg burst sim"` measured `bytesPerFrame.sim` **40,000.75** (24,000,448 B over the 600-frame window, the lower of [0028](0028-zero-gc-two-measured-windows.md)'s two windows) but `attributedBytesPerFrame.sim` **0**. A temporary, fully-reverted debug dump of the raw `HeapProfiler.stopSampling` payload ruled out "no samples": **300,018 real samples**, 24,000,564 total sampled bytes, **79.997 B/sample** average — the profiler was sampling fine. The cause was call-tree ancestry: `src/test/harness-worker.ts`'s `runOp` called `coreTick()` and, as a **sibling** statement, `applyStepControl(...)` (where the control's allocation lives). `coreTick`'s own subtree ended before the control ever ran, so `attributedBytes(profile, ['coreTick'])` — "inclusive bytes under a node named in `roots`" — correctly returned exactly 0 by its own definition. Not a bug in the function; the control hook sat structurally outside the named root.

**The wider instance.** The same shape turned up on `main`, on every production-topology page, not just `gc-loop`. With real `software.frames: 600` clean baselines measured and provisional budgets set locally (reverted, never committed), `neg object main` failed to trip on **all five** pages, reading identical to its own clean baseline (topology/echo/gen/terrain/input: 12, 0, 12, 80.02, 160.17333... respectively, unchanged with or without the control). Cause: `src/test/gc-page.ts`'s `run()` applied `main`'s control as a call **sibling** to `drive(f)` inside `run`'s own loop body, while every page's `attributionRoots` for `main` names `drive` (or, for `topology`, the still-narrower `stepFrame`/`stepTick`) — never `run` itself. `gc-loop` only looked healthy because its own `attributionRoots` for `main` happens to be `["run"]`, the one root wide enough to contain everything, control included — not because its mechanism differed.

## Decision

**1. Nest the control hook inside the attribution root; never widen a root to contain a control.** `src/test/gc-page.ts`'s main-isolate control now fires as the first statement inside a function literally named `drive`, which then calls the page's own `opts.drive` (or the old default's `stepFrame`+`stepTick`) as a nested call. `src/test/harness-worker.ts`'s `coreTick` now calls `applyStepControl` as its own first statement; `runOp` just calls `coreTick(seq)`. `topology`'s `attributionRoots` for `main` moved from `["stepFrame", "stepTick"]` to `["drive"]` — not a widened root, since `drive` is the direct parent of the exact same calls already covered, plus the now-correctly-nested control. The rejected alternative — widen `attributionRoots` to a function that already encloses both the real work and the control (`run` for `main`, `runOp` for a worker) — is recorded explicitly because it was live and cheap to do: it would make clean assertion B attribute harness scaffolding to the engine, weakening the exact assertion the control exists to police, and it would raise every clean baseline for a reason that has nothing to do with engine allocation. A control that fires outside the measured region was never testing the instrument; it was testing itself.

**2. Software mode uses attribution only for `main`; every other isolate uses raw `bytesPerFrame` in both modes.** With hooks nested, the acceptance run (`object` control, software mode, `--repeat-each 5`, all six pages × every isolate, 95 executions) passed 90/95, failing 5/5 bit-identically on exactly one isolate: `topology neg object client`. Its `attributedBytesPerFrame.client` read **0.02666666666666667** every run (16.00 B over the 600-frame window — exactly one object's worth, not zero) against 16 expected, while `applyGcHook`'s real, full contribution in that same window — `byFn.client` showing `applyGcHook@worker-auto-*.js:501: 9616` (~600 real wake calls × ~16 B, no dead-store elimination) — landed almost entirely on a call-tree node with no `body` ancestor at all. V8 had inlined `body()` into its caller (`runBlockingLoop`) for essentially the whole window, on every one of 5 independent page loads. Of the 19 worker/main isolate–control pairs in that run, 12 share the same `body()`-first-statement pattern (`src/worker/{client,gen,sim}.ts`: topology and echo each contribute `client`+`sim`+`gen0`, gen/terrain/input each contribute `client`+`gen0`); 11 of those 12 tripped 5/5, and only `topology`'s `client` failed, at 0/5. `topology`'s `client` worker is the smallest, hottest instance of that shared file across every gc page — no real terrain/gen/camera work, just the `fx-hash` fixture — making it TurboFan's best inlining candidate; `terrain`/`input`'s own busier `client` bodies did not show the same behaviour at this repeat count. So this is where a JIT heuristic happens to land, not a structural property of the mechanism, and no set of function names or root choices closes it. Software mode therefore reads `attributedBytesTotal` only when `name === 'main'`; every other isolate, in either mode, runs the identical raw-bytes check against its own hardware `bytesPerFrame`/`bytesPerMessage` budget, since no worker isolate ever touches WebGPU and its raw count is exactly as clean in software as in hardware. Measured (stability check, `--repeat-each 5`, all 9 worker-isolate/control pairs across the 5 production pages plus every page's own clean run, 70 readings total): clean **0.70–2.52 B/frame**, control **16.84–29.55 B/frame**, against the strict **8 B/frame** budget — a minimum ~14 B/frame gap between the highest clean reading and the lowest control reading, with the budget sitting cleanly between the two clusters on every isolate. Not perfectly bit-stable, recorded rather than rounded off: `gen`'s `client` control reading was bimodal (3 runs ~17.12, 2 runs ~29.49, plausibly [0028](0028-zero-gc-two-measured-windows.md)'s own one-off JIT-installation mechanism, now landing on a worker's raw total instead of `main`'s); `input`'s `client` clean reading had one low outlier (0.83 vs. four at 2.52). Neither cluster ever came close to the 8 B/frame line. Re-run under this design at the full acceptance bar (`--repeat-each 5`, all 6 pages × every isolate, 125 runs): **125/125 passed**, `topology neg object client` among them, now tripping via its raw total (16.84 against budget 8) exactly as it already does in hardware mode.

**3. `main` keeps attribution for a different reason than 0016 states, and that correction is part of this decision, not a footnote.** 0016 §3 caveat b, quoted verbatim: *"On SwiftShader (Linux CI) the spike's 4096-quad scene drained at ~58 ms/frame and N = 600 timed out; with N = 100 the frame function still cost 64.2 B/frame with zero GCs, but total/N read 277 because harness overhead no longer amortises. On a software adapter the test therefore uses a trivial scene or smaller N and asserts on bytes attributed to the engine's frame and tick functions (exact constants in the spike: 38 424 B main, 0 B worker per 600 frames) instead of total/N."* Its stated rationale is purely arithmetic — a slow scene forces N down, and a small N means per-run harness overhead (CDP round trips, `page.evaluate`, `HeapProfiler` bookkeeping) no longer amortises across enough frames — and it names "the engine's **frame and tick** functions", i.e. both `main`'s role and a worker's, for the same reason, not a `main`-specific one. M10's own decision 3 (the same round) fixed `software.frames` at 600, identical to hardware `FRAMES`, precisely so [0028](0028-zero-gc-two-measured-windows.md)'s two-window rule reads identically in both modes. Under N = 600, 0016's own stated arithmetic gives harness overhead the same 600 frames to amortise across in both modes — **its literal precondition for needing attribution at all no longer holds, `main` included.** `main` keeps attribution anyway, but for a reason that must be stated as new rather than borrowed from a precondition that no longer applies: once decision 1 nests the control inside the root, the nested control becomes a **live inlining detector**. If V8 ever inlines `drive` away the way it inlined a worker's `body()`, `main`'s own negative control fails loudly instead of a clean test passing quietly on an unrepresentative total. A worker isolate gets no equivalent benefit — it carries no software-adapter-specific reason to keep test-harness scaffolding in its attribution path — which is exactly why decision 2 moves every worker off attribution entirely rather than trying to fix its inlining exposure the same way.

## Alternatives rejected

- **Widen `attributionRoots` to enclose the control** (`run` for `main`, `runOp` for a worker) instead of nesting the hook. Live and cheap, considered and rejected: it would make clean assertion B attribute harness scaffolding to the engine, weakening the assertion the control exists to police, for a reason unrelated to engine allocation. Decision 1.
- **A separate investigation into V8 inlining before trusting any software-mode negative control.** Not needed: decision 1's nesting already turns the mechanism into its own detector — a control that trips reliably is direct empirical proof the root survived as a distinguishable call-tree node in that window, so `topology neg object client`'s 0/5 is itself the finding, not a reason to study further before trusting the other 11/12.
- **Keep 0016 caveat b's original rationale as the reason `main` keeps attribution.** Checked against the text, not against memory: caveat b's stated mechanism is arithmetic (harness overhead not amortising at a shrunk N) and names both roles equally; `software.frames: 600` removes that precondition for both. Restating the old rationale for `main` alone would misattribute the design to a justification the source text does not give it.
- **Drop attribution from `main` too, now that its originally-stated precondition no longer holds.** Not adopted here — the mechanism is already correct and tested (125/125, both modes) and now serves the live-inlining-detector purpose above, which is a reason `main` has and no worker has. Left open rather than decided; see Consequences.

## Consequences

- **A negative control that stops tripping in software mode is a signal about the instrument, never something to fix by widening a root or relaxing a budget.** Stated plainly for whoever next sees one fail: on `main`, a control that stops tripping means `drive` stopped surviving as its own call-tree node, the same failure mode `topology neg object client` hit here; the fix is 0016 caveat b's trivial-scene option or a fresh ADR, never a wider `attributionRoots` or a softer margin.
- `main`'s `drive` root stays exposed to the same V8-inlining risk that hit `topology`'s `client` worker. This is accepted, not overlooked: nothing in this design prevents a future page or Chromium version from inlining `drive` away, but decision 1 means that failure is loud (the control stops tripping) rather than silent.
- **Open question, deferred to M36b** (`docs/plan/deferred-ledger.md`): whether `attributedBytesPerFrame`-based attribution is needed on `main` at all, now that `software.frames: 600` removes 0016 caveat b's own stated precondition for every isolate. Dropping it would delete the residual inlining exposure on `drive` rather than police it with a live detector — a simplification, not a defect fix, since the current design is correct and tested.
- **Hardware mode is unchanged and was never affected.** Attribution is a software-mode-only code path: `packages/engine/tests/browser/gc/analyse.ts`'s `verdict()` reads `attributedBytesTotal` only when `mode === 'software' && name === 'main'`; every other isolate, in either mode, runs the identical raw-bytes check (`rawB`) against its own hardware budget. `gc-loop`'s now-dead `software.isolates.sim` entry was removed from `packages/engine/budgets.json` rather than left stale; `page.software.isolates` only ever needs a `main` key from here on. `packages/engine/budgets.json`'s five re-derived `software` blocks (`ceil(measured clean) + 8`, `frames: 600`, `main`-only): `topology` 20, `echo` 8, `gen` 20, `terrain` 89, `input` 169 — every clean reading bit-identical across every repeat measured.
