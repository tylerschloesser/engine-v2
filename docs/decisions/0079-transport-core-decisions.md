# 0079: Transport core: decisions made while building it (M42-M56)

Status: Accepted (2026-10-11). §23 (milestone 56, 2026-10-12) records the scenarios' measurements: §11's spread is 24 / 88 and stays, §16's cursor is not needed, question 11 measured on a balancer. §22 (milestone 55, 2026-10-12) builds undergrounds on segment-less hidden lines with pairing derived in the tick, no engine change. §21 (milestone 53, 2026-10-12, built) makes the spawner schedule transport state and the engine's insert, amending §19 (a) and §20 (a). §2 and §5 amended by §12-§14 (milestone 43); §11 and §14 amended by §15-§16 (milestone 44); §16's size figure amended by §17 (milestone 46). §17 (c) narrowed and its size figures amended by §18 (milestone 47). §18 (d) resolved by §19 (milestone 47b). §19 (a)'s declaration survives a restore by §20 (milestone 48). Amends [0076](0076-transport-lines-engine-game-split.md) §7 (the state hash covers the transport store once it has ever held a line) and §8 (the arena's real size and where it is reserved); settles the save behaviour 0076 Consequences assumed. Implemented by milestone 42 and amended through milestone 56 (`docs/plan/42-transport-core.md` and the later briefs, at tag `belts-complete`); their Deviations hold the evidence.

## Context

Milestone 42 built `engine::transport` as sim state in `Store<G>` with the B1 run store of [0077](0077-transport-item-representation.md) A6. Building it moved six things the ADRs had stated or assumed: what the state hash covers, how runs are encoded, what a restored world must carry, how the host-tick-only rule is enforced, how much memory the arena takes and where, and what happens to a save written before the store existed. Each is a technical decision; this ADR records them so that `Store`, `persist` and the TypeScript loader agree with the text.

## Decision

**1. The state hash covers the transport store once the store has ever held a line.** `Store::encode` always writes the transport section (last, after the wake queue); `Store::hash_state` skips it while the store is pristine (`next_id == 1` and no line; `next_id` is encoded, so a restored world hashes like the live one). Every world that never creates a line keeps its pre-M42 hash: no fixture golden and not the reference game's `full-game.json` changed, which is the proof that milestone 42 changed nothing for a game without belts. Amends 0076 §7's "byte for byte": the section enters the hash with its first line and never leaves it (a store that destroyed every line still hashes it: `next_id` stays above 1).

**2. A later run's encoded distance is `gap + SPACING`**, the distance from the item ahead, not the in-memory free gap. With the free gap encoded no byte pattern could violate spacing and the codec's validation would have nothing to reject; with the distance encoded, decode rejects any `dist < SPACING` and any position past `len - 1` with `CodecError::Malformed` (pinned by `transport_codec_round_trip_and_rejects_spacing_violation`). The per-line record is `id, len, speed, out, sunk, jam, run_count, runs (item, count, dist)`, then `next_id` (`transport/codec.rs`).

**3. The jam cursor is encoded.** A re-walk from the front can merge a same-kind pair the cached skip leaves unmerged (a pair the `u16` count guard refused whose front run later shrank), so a restored world without the cursor would advance differently from the live one. The cursor is sim state; `touched` and the computed `jam()` summary are not.

**4. The host-tick-only rule is a phase flag.** `Authority` carries `in_genesis` and `in_tick` (set by `Sim::step` around `G::tick` only); `transport_mut()` is `Ok` when either is set and otherwise `Err(Unknown)` behind a `debug_assert!` naming 0076 §6, so it fires in `apply` and in `on_player`. `TickCx` answers `Ok` itself, `Migrating` answers `Ok`, `Predicting` marks the overlay and answers `Err(Unknown)` (`transport_in_apply_is_unknown`, `transport_predicting_is_unknown`, `transport_tick_and_genesis_are_ok`).

**5. The arena is reserved once, when the world params arrive, and it is 7 MiB at the defaults, not 4.** `Store::new` holds an empty store with no arena (a replica and a plain test store pay nothing); nothing is reserved until `set_transport_caps` applies `WorldParams::{max_lines, max_items}`, which every host genesis, restore, upgrade, migrate and test-replay path does exactly once (the review of milestone 42 found the defaults reserved first and the world's caps on top; fixed before the commit). A B1 run node is 16 B (an 8 B run plus two `u32` links), so 262,144 items are 4 MiB, lines about 2 MiB, scratch about 1 MiB: 7 MiB against 0076 §8's nominal 4 MiB. On the baseline phone that is most of 0007 §8's 8 MiB slack. **The world-param default is 0** (belts are opt-in: a game that never sets the caps reserves nothing); 0076 §8's figures are the recommended caps a belt game sets (`fx-belts`' scenarios set theirs; the reference game sets them in milestone 51, which also revisits the netcode soak's 8 MiB sim arena). Found by CI the same day: the soak ran the reference game on its deliberately small arena and the 7.5 MiB default reservation trapped it (`arena exhausted: requested 4,194,320 bytes with 7,948,228 live, reserved 8,388,608`). Milestone 57 measures the phones. The host's memory-split check (`Host::init`) must count the arena (milestone 42's follow-up), else the budget it enforces cannot trip for the biggest new allocation.

**6. A save written before the store existed is refused, not replayed.** `CONTAINER_VERSION` is 2. The Rust readers return `PersistError::ContainerVersion` (`snapshot_old_layout_is_incompatible`). The TypeScript loader had treated a container mismatch like a bad CRC and fallen back to a genesis replay of segment 0's log (`docs/architecture/persistence.md`, now superseded on this point), which would present a long-lived world as `recovered` at the state it had at the end of its first 4 MiB segment: silent partial loss. From milestone 42 a container mismatch is `WorldLoadError.kind = 'container'`, surfaced to the client as `save-incompatible`, every stored byte untouched. Tyler is told in the milestone report: existing reference-game saves refuse to load; there are no live players ([0076](0076-transport-lines-engine-game-split.md) Consequences); no migration is written.

**7. Two primitives moved forward; two hooks changed shape.** `insert_at`/`remove_at` (0076 §3, planned for milestone 43) exist from milestone 42 because six of the twenty rule cases need them; `destroy` is minimal until 43. `Line::jam()`/`Line::touched()` are `Transport::jam(line)` (computed on read from a `held` bit `advance` sets) and `Transport::touched(line)` (an epoch mark, no per-tick clearing pass); milestone 47 may change them when the tracker is built.

**8. A plain hand-off needs `target.len >= feeder.speed`.** An item at the feeder's front moves at most `speed` in one tick, so it lands at `target.len + p` with `p >= -speed`; a target shorter than the feeder's speed would put it below 0 (the review found the `u32` cast wrapping to a position of about 4.29 billion that decode later rejects, making the world's snapshots unrestorable). `set_out(a, Next(b))` and `set_speed` refuse the violation with `BadSpeed`, decode rejects a stored graph that has it, and milestone 43's `split`/`shrink`/`rescale` must refuse to shorten a target below its feeders' speeds. 0076 §1's `speed < len` is the within-line half of the same rule.

**9. Belt motion marks the world dirty.** `advance` returns whether anything changed and the host marks the world dirty on it, as it does for every write through `transport_mut`; before this, a world where only belts moved was never snapshotted ("every 1,200 ticks if dirty", and at pause only if dirty) and reloaded with its belts rewound.

**10. `insert_back` lands before the tick's move.** The landing `max(len - speed, tail + SPACING)` is the item's position before this tick's `advance` (which runs after `G::tick`, 0076 §2), so an item inserted at tick `T` sits at `len - 2 x speed` when `T` ends: it entered one tick's travel inside the back edge and then moved. A `Sink` line with `len < 2 x speed` sinks it the same tick, legal and conserved. Milestone 42's brief had stated the opposite ("sits at `len - speed` after this tick's move"); the spike and the production code agree with this section, and milestone 41's spawner replay on the client is built on it.

**11. A cut cycle moves every item by at most `speed` per tick.** The update order cuts a cycle at its lowest `LineId`, which advances first and whose front therefore lands on a line that has not advanced yet. Milestone 42 left such landed items in place for the rest of the tick (a per-line count of items landed from a not-yet-advanced source), which bounded them against the target's tail *before* it moved: milestone 44b's ring property test showed a packed block crossing the cut spread by `speed` for good, the cut carrying `speed / (SPACING + speed)` items per tick (0.27 at speed 24 against 0.375). The rule as corrected (milestone 44's cut round): the first line of a simple `Next` cycle bounds its front item against its target's tail *as it will be after the target's move*, like every other line does, the target's move being found by a dry pass around the cycle to a fixed point (at most 4 passes; a rotating or compressing loop settles in 2; with no fixed point the line falls back to the target as it stands), so a fully packed simple loop rotates at belt speed with every gap exactly `SPACING`; a landing at the cut may for the rest of that tick sit inside the spacing of the target's unmoved tail (down to `target.speed` behind it), which the target's own advance resolves before the tick ends (asserted in debug builds: every gap above `-SPACING` and positions strictly increasing at the end of every line's advance). A loop with a squashed pair (§12) may reach no fixed point in 4 passes and falls back to the target as it stands (deterministic, tested; the front holds that tick). **Known limitation, trigger milestone 56's loop scenarios:** the dry pass handles simple `Next` loops only; a loop whose links include a `Fork` or a `Merge` (a splitter loop, a sushi belt) still bounds its cut line against the unmoved tail and a packed block spreads by `speed` at the cut. **Known cost, milestone 45/56's input:** the dry pass has no jam cursor, so a stalled loop walks its runs on every pass (up to 4 x its runs per tick); a free loop costs O(lines) and a line not on a loop nothing extra. Separately, a fresh landing across a cut records `speed - moved` as a per-line budget and the target's advance moves such items by at most that budget (two landings in one tick with different budgets: 0; a mid-line merge landing: `target.speed - feeder.speed`), so an item moves at most `speed` in one tick in every cut shape, including side-loads onto a faster line and cuts that are not simple `Next` cycles. Built in milestone 42 in about 40 lines, inside the early-exit path; pinned by `transport_cycle_cut_moves_every_item_exactly_speed` and the per-item reference test's own cut rule.

**12. A squashed pair is stored exactly, as a negative run gap (milestone 43; amends §2).** `rescale` must keep Factorio's measured behaviour (12 §3e): a full outer curve lane (295 positions, five items) reshaped to a straight (256) cannot hold five items `SPACING` apart, so pushing the pair apart would refuse a reshape the game cannot refuse, and moving items an edit should not move was rejected in the brief. `Run.gap` is therefore `i32`, negative for a pair closer than `SPACING` (never below `1 - SPACING`: positions strictly increase; a rescale that would put two items on one position is `NoRoom`); `advance` moves a later run by `clamp(gap + d_prev, 0, speed)` (12 §3c's rule, which a packed pair reduces to); a per-line `squashed` flag (derived, never encoded: a stale flag changes nothing) turns the free-moving early exit off while a negative gap exists; `join` keeps a squashed boundary pair the same way (legal across a hand-off, 0077 A6b). Decode now rejects only `dist == 0` and positions out of range; a `dist` in `[1, SPACING - 1]` is a legal squashed pair. Lines are capped at `MAX_LEN = i32::MAX` (`TooLong`).

**13. Segments ride a presence bit; geometry is pooled.** A line's segments are encoded after its runs only when bit 7 of its `out` tag is set, so a line without segments is byte-identical to its milestone 42 record and no golden moved. Segments are pooled at `4 x max_lines` records of 32 B (not 16 per line); `MAX_SEGMENTS` is 16 per line and `MAX_LINE_TILES` 4,096 tiles per line's path (`set_segments` is `Full` past either; a longer or more winding belt chain is two lines, the game's call when it merges). The tile index is `8 x max_lines` entries of 16 B plus 4,096 entries of merge room, rebuilt on decode and maintained by every edit; `chunks_of` and `anchor` are computed on call. Any surgery that changes a line's `len` clears its segments; the game re-registers them. `chunks_of`, `segments` and `lines_at` take callbacks (`TransportRead` is `dyn`); `chunks_of`/`anchor` take `ChunkDims`.

**14. The arena at the recommended caps is 16.2 MiB (amends §5's 7.5).** Line record 80 B, 256 B of geometry per line (segments and index), 16 B per run node, 64 KiB merge room: 16,220,176 B at 32,768 lines and 262,144 items; still 0 when a game sets no caps. Two ways to shrink it if milestone 57's phone measurement needs them: size the tile index by a tile budget rather than 8 per line (the reference scale needs about 100k entries, not 262k), and move the line record's four derived fields out of the arena. Known cost, measured in milestone 43 (`slow_geometry_upkeep_cost`: one line's `extend_back` plus `set_segments` with the index at 262,136 entries is 202 µs median in release on the Mac, about 0.4 ms per two-lane belt tile) and decided by milestone 45/52: removing a line's index entries and merging new ones is O(index) per edit (a `retain` and a merge over up to 4 MiB), so a drag placing several tiles in one tick pays several passes; if the reference game's placement tick is over its budget on the phone the index is bucketed per chunk.

**15. `Merge` and `Fork` as built (milestone 44).** The front item of a merging or forking line has no leader beyond its own feeder: when it would cross (`p < 0`, overshoot `o = -p`) it tries to transfer; on refusal it waits at 0 and the walk squashes the rest; on success the next item tries in turn (big steps). *Merge*: the landing is `clamp(at - o, 0, target.len - 1)` and transfers iff the target, as it stands after its own advance this tick and earlier landings, has `SPACING` clear on both sides (`insert_at`'s rule); any `at` is accepted and a merge target has no §8 bound (the clamp covers a target shortened later). *Fork*: a one-bit toggle per forking line names the preferred target (`false` = `a`); room is the plain hand-off rule on each target (§8 holds for both targets, so `len - o` is in range); preferred, else other, else wait; the toggle flips only when the item went to the preferred side and is cleared by every `set_out`; it is encoded only with a fork (tag 4: `a`, `b`, toggle), so a line without a fork keeps its earlier bytes and no golden moved. *Order*: Tarjan over the two links; a component advances its lowest id first, then depth-first post-order over its links (`a` before `b`), which for a simple cycle is milestone 42's order. *Redirects on surgery*: a destroyed target turns `Next`/`Merge` into it into `DeadEnd` and a fork with it as a target into `Next(other)`; `split` moves `Next` and fork targets to the back part and a merge only if its entry point is at or past the cut (a landing straddling the cut clamps to 0 on the back part and may form a legal cross-boundary squashed pair, §12); `join` renames `back` to `front` everywhere, adds `front.len` to a merge's `at`, collapses a fork with both targets on `front` into `Next(front)`, and refuses when `front`'s own output names `back`; `extend_front` adds `by` to every merge's `at` on the target, `shrink_front` subtracts it (an entry point that falls off the front becomes `DeadEnd`), `rescale` maps it by `floor(at x new / old)`; `extend_back`/`shrink_back` leave it. `set_out` with an identical output is a no-op (the toggle keeps its state, so a game re-applying a region's outputs does not bias its forks). `insert_at`, like a merge landing and like a plain hand-off onto an empty line, checks spacing on its own line only (0077 A6b): an insert or a landing within `SPACING` of a line's front may sit closer than `SPACING` to the next line's tail, a landing within `SPACING` of the back closer than `SPACING` to the feeder's front, and a hand-off onto an empty line shorter than `SPACING + speed` lands within `SPACING` of the tail of the line after it (the reference game's shortest lane, 106 positions at speed 24, is above that bound); each is a legal squashed pair across a hand-off that the squash rule resolves, and milestone 44b's spacing property excuses exactly those pairs and pins their counts. A transfer touches both lines (§9). The merge landing's clamp to 0 is the asymmetry §8 refused for `Next`: unreachable for the reference game (`at >= SPACING > speed`), reachable at speeds 72 and 96 and accepted there because an entry point is a geometric fact the game set, not a layout the engine can refuse.

**16. A merge landing on a line that has not advanced this tick stays put (amends §11; the record is 88 B, 16.5 MiB at the recommended caps, amending §14).** A fork's landing is a back landing, which §11's count already covers; a merge's can fall in the middle of a line later in the update order (only across a cycle's cut, since the order puts every target before its feeder otherwise). Refusing it would deadlock a loop whose side-load is the cut link; letting it move again would break §11. So the landing applies `insert_at`'s room rule over the line as it stands, never joins a moving run, and either joins the cut's back block or becomes a one-item run marked `count == 0` that exists only inside `advance`: the line's walk restores the count, moves the item by at most its remaining budget of §11 (`target.speed - feeder.speed`; 0 at equal speeds, so it keeps its place), holds the items behind it and skips the early exit. Pinned by `merge_across_a_cut_stays_and_holds` and by the per-item reference's merge-cut cycle. The line record grows to 88 B (`alt_slot`, `toggle`, `fresh_mid`): 16,482,320 B at the recommended caps. Known cost: a blocked side-load walks its target's runs to the entry point every tick it waits, from the nearer end (measured, `slow_blocked_sideloads_cost`: 50 blocked side-loads near the back of a 1,000-tile main line of 4,000 alternating-kind runs cost 7.7 µs median per `advance` in release, against 164 µs walking from the front); a per-merge cursor is the fix if milestone 45's `tick.beltsLargeMs` shows it.

**17. Replicating structures (milestone 46; amends §16's size figure).** A line's structure (`len`, `speed`, `Output`, segments) reaches a client as a whole-value `Put` in frame section 12 (`LineStructs`; `wire/CLAUDE.md` holds the bytes) and leaves with `Gone`; items never cross here (0078 §6). What moved while building it: (a) **chunk snapshot entries carry no structures**: an entry has no count byte to mark where they would start, and adding one would move the snapshot golden and every exact byte row; instead a chunk with anchored lines always enters by snapshot (never pristine), its anchored puts are priced into the chunk bucket and ride the same frame's section 12, and a client applies the whole frame before it checks the frame's `Hashes` (section 9 precedes 12). (b) **The per-chunk hash covers the anchored structures in tile-index order**, not by `LineId`: the index is fully sorted by content (`(y, x, line, offset)`), so host and replica agree whatever the arrival, placement or surgery order, and the hash needs no scratch sort. (c) **Every put shares one byte budget per frame**, a quarter of the frame buffer (16,384 B at the 64 KiB `Tx`, about 470 one-segment puts; the snapshot bucket may already hold half a frame), halving per consecutive overflow like the bucket's cap, the first put always sent so a frame always progresses; puts over it stay pending (never dropped), `Gone` is never budgeted, and a frame that defers a structure the client holds or one anchored in a held chunk carries no chunk hash, so hash-all never compares against a stale structure. An all-or-nothing send stalled a connection for good once the puts due in one tick exceeded `Tx` (a same-epoch reconnect over the bench window: 2,500 puts, 87 KB), which the review found and `host_puts_spill_over_frames` pins. (d) **`structure_version` is the tick of the last structure change**, derived and never encoded, bumped by every structure write and destroy and by no item write; the per-tick change list holds `max_lines / 4` entries and on overflow the host reconciles every line once (a full-size list would cost 8 B per line and push the phone pair under 16,384 lines). (e) **`Welcome` carries the world's caps behind flag bit 2**; a world with caps 0 keeps its bytes; the replica reserves what the world declares (one rule, no second cap), and a `Put` it cannot hold is counted (`transport.structsDropped`) and reported once per session against its anchor chunk. (f) **The replica's `lines_at` inside a held chunk answers `Ok` while a put may still be pending**: accepted knowingly (a renderer tolerates a late structure; prediction answers `Unknown` for every transport read, 0079 §4 extended in `predict/predicting.rs`); revisit if M47's forecasts need the set complete. Sizes: the line record grows by 5 B, so the recommended caps reserve 16,646,160 B (was §16's 16,482,320) and the phone pair of milestone 45 (16,384 lines, 131,072 items) is 8,355,856 B. Measured on the bench world: 34.9 B per one-segment structure (2,500 puts, 87,188 B for a 121-chunk view at the densest window; the world is 220 tiles wide, so 144 chunks do not fit), 0 B of section 12 per tick without a structure change. Known costs for milestone 48: a replica put rebuilds its tile index entries (O(index), §14), and a leave frame calls `chunks_of` once per held line per connection.

**18. Forecasts, the engine half (milestone 47; narrows §17 (c), amends §17's size figures).** The scheme's changes are 0078 A8; what moved here: (a) **the tracker is `Transport`'s, host-only** (`is_replica()` gates every hook), derived and never encoded or hashed, its memory reserved with the arena at `set_transport_caps` by role (§5's rule): a host reserves the tracker, a replica the follower and none of the run nodes, update order, Tarjan scratch or change list; `reserved_bytes` and `replica_reserved_bytes` report each, and the phone pair is sized by the larger (A8 has the figures). (b) **§17 (c) is narrowed for a held line**: a deferred update or correction of a line the client holds goes `Gone` and is put again later with its list, instead of staying pending with the chunk hash withheld; a put of a line the client does not hold stays pending as before (`host_puts_spill_over_frames` proves that path, `host_held_update_over_budget_goes_gone_then_put` this one). (c) **The due-tick heap is indexed by line** (one due per line, the nearest); the per-tick hand-off log holds `max_lines / 2` entries and on overflow the lines involved resend their lists; a full segment pool resends the line next tick; the tick's records are cleared by the next tick's first hook only after `Host::seal` ran (asserted in debug builds). (d) **The bench gate was red before this milestone and stays red until 47b**: `slow_tick_belts_large` was not among milestone 46's verification commands, and this milestone's gate measured 1.190-1.224 ms at `286a688b` against the 0.8815 baseline (frames 0.70 to 0.98 ms: the delta-collapse estimate in `Host::build_frame` prices every chunk with deltas every tick, and milestone 46 added `anchored_bytes` to that price; the bench's cycling spawners put a delta in every chunk every tick) and 1.310-1.357 ms with the tracker (+0.12-0.16 ms: the front checks, 1,090 `insert_back` hooks a tick, about 330 arrivals a tick for the bench's undeclared spawners). The brief's 1 ms criterion holds and the 5 ms limit is far; nothing re-records a baseline before the cost is reviewed (0069 §7), so milestone 47b caches the collapse price per chunk by `structure_version`, declares the spawners, measures, and re-records. (e) **§17 (f) stands**: `lines_at` during deferral is unchanged; forecasts need the set complete only for lines the client holds, which (b) guarantees.

**19. The declaring fixture, the bench regimes and the collapse price (milestone 47b; resolves §18 (d)).** (a) **A game declares its spawner after its first step on the tick it joins** (`set_spawner(line, Schedule { period, acc, kinds, next })` with the accumulator and next item as they stand after that step; the tracker arms the rule from the next tick). `kinds` is 0 for a fixed-item spawner: the engine's `kinds == 0` means "always `next`", and `kinds` 1 would mean "only item 1" (the brief's 1 was wrong). `fx-belts`' `Thing::Spawner` and `Thing::Cycling` declare so; over 600 ticks on five 1/64 regimes `spawner_mismatches` and `spawner_declarations_dropped` are 0 and no insert is routed as an arrival after tick 1 (`belts_spawner_declares_schedule`); the bench's 13.4 KB a tick of arrivals for undeclared inserts are gone (54,153 B of frames a tick, M46's figure). A declaration is still lost on restore (milestone 48). (b) **The bench world's scheduled edits are game rules, not requests**: `Thing::Jam` (one per toggled sink of M44b's `SaturatedView`, `set_out(Sink | DeadEnd)` on the ticks its half-period changes) and `Thing::Inserter` (M40's `2,000 / scale` inserter-like calls a tick from a stateless SplitMix draw of `(seed, tick, call)`) ride the `"spawner"` list and are never written, so they cost no delta; a `BenchRegime` (`Mixed`, `InserterLike`, `MixedEmpty`, `SaturatedView { jam_pct, period, speed }`) rides in three more marker tiles, plain for `Mixed`, so the bench golden and every earlier spec hold. (c) **The host caches each chunk's structure price** (`host::lines::StructPrices`): the delta-collapse estimate and the enter bucket price a chunk's snapshot with its anchored lines' puts every tick the chunk has deltas, and the bench's spawners put a delta in every chunk every tick, while structures rarely change. An entry is `(chunk, newest structure_version among the anchored lines, their count, bytes)`, valid while both read the same: an anchor moves only with a structure change, stamped later than any version the entry saw, so a line changed, created or moved in raises the version and one destroyed or moved out alone lowers the count; lists (`run_list_bytes`) are priced live on the same walk; the table is reserved at attach for `max_lines` entries and cleared when the store is replaced (genesis, restore). Measured alone: frames 1.16 to 1.05 ms, -0.10 ms. (d) **The bench baseline moves to the reviewed figure.** `slow_tick_belts_large` reads 1.264 ms (the median of three runs at quiet load, 1.241 / 1.274 / 1.264, 1-min load 1.9-3.3, a fourth 1.298; the implementer's three read 1.256-1.280; all seven within 4.6 %) against M45's 0.8815: +0.38 ms, inside the brief's 1 ms criterion. Its parts: M46's structure replication about 0.3 ms (§18 (d): `build_frame` priced every chunk's anchored structures every tick, now cached), M47's tracker and section 13 about 0.1 ms, and `build_frame`'s remaining walk over anchored lines and the list bound for eight maximum views; the 5 ms limit and the workload stand. (e) **The bytes gate lifts chunk pacing** (0078 A9's reason); the consequence for the reference game (milestone 53) is that its spawners must not write an entity per insert, or the chunk deltas alone would collapse chunks and re-put lists under production pacing.

**20. Replication robustness, the engine half (milestone 48).** (a) **A game re-declares its spawners through `Game::declare_spawners(&RestoredCx<Self>, &mut dyn FnMut(LineId, Schedule))`**, default nothing, called by the host once after every `Sim::from_parts` (restore, upgrade, migrate; never at genesis, where a game declares on join): the schedules are derived and never saved (§19 (a)), so until then every spawner insert routed as an `Arrival`. `RestoredCx` is the restored world as a `WorldRead` plus the active-list reads (`active_len`, `active_at`): a game keeps its spawners on a list and `WorldRead` cannot enumerate outside a rectangle (the brief's `&dyn WorldRead` could not see them). The host then closes the tracker's tick once (`Transport::forecast_close_restored`), as the saved tick's end would have: without it the declarations stayed unarmed through the first restored tick and replayed from a stale accumulator (393 mismatches on the 1/64 world). Rejected: a `TickCx` "restored" flag (one more phase flag read inside `tick`) and a per-tick `has_spawner` read. (b) **A chunk's version moves only for what a replica can see.** `Host::tick` stamps a tile write and every scope of an entity that existed at tick start as before, but an entity born this tick (id at or past the tick's first new id; ids are never reused) stamps only the chunks it overlaps at tick end: a request entity spawned and despawned in one tick stamps nothing, as on the replica, which bumps only on an applied delta. The region hashes agree and the resume hint keeps such a chunk; the `O = 200` workaround in `tests/netcode/belts.test.ts` is gone. Known limit, recorded: an entity that existed at tick start and moves twice in one tick, or moves and then despawns, stamps the chunk it passed through on the host while the replica's coalesced put bumps only the tick-start and tick-end footprints: the region hash differs for that tick. No `fx-belts` entity moves; a game that moves an entity twice in a tick meets it (milestone 51 checks the reference entities). (c) **A lost frame re-snapshots the held chunks it changed**, the rule the lines already follow for the lines a lost frame named (0078 A8): `Host::seal` clears the change log after every connection's build, so an overflowed frame's `ChunkDeltas` are gone; every held chunk any delta of the tick was scoped to is queued for a `Resnapshot` through the bucket (`lost_resnapshots` counts them; `collapsed` reserved at 160, the held set). Every lossy window had raised client chunk-hash desyncs (M47 read "2-16 a window": `DesyncLog::len()` caps at 16, so a lower bound); now 0 over 1,024 lossy ticks on the lined and the `NO_LINES` worlds, at +673 and +548 B of snapshots per 1,024 ticks, plus the anchored lines' re-puts (a collapsed chunk's snapshot force-re-puts its lines, so a list named by the lost frame can go twice; milestone 48's Deviations hold both figures). (d) **`Pacing::take_bundle` never panics**: it returns `Err(BundleTooLarge)` when the first held frame is longer than `out` (nothing written, the frames stay held, `bundles_too_large` counts it, nothing emitted that tick); its precondition is that `out` is the connection's `Tx`, which production always passes; only a test varying its buffer reaches the error. (e) **The frame hold is sized from `Tx`**: `hold_bytes(tx) = 2 (tx + 10)`, since the emission rule holds at most one frame left from a bundle plus the tick's own (a hold of half the buffer is due and a due bundle takes every frame that fits after the first), where it was 8 KiB and grew under a level-4 bundle of belt frames; the per-frame chunk scratch lists are reserved at 160 and the snapshot scratch at `Tx`. `no_alloc_connection`'s degraded window (level 2 then 4 on the lined world, a 24 x 16 paint a tick) proves 0 B of host growth while degraded; its bundles stay far under half the buffer, so the bound itself is pinned by a `pacing` unit test that drives the real emission tail with `Tx`-sized frames to the worst case, two records. Cost: `slow_tick_belts_large` 1.226 / 1.256 / 1.273 ms against the 1.2638 baseline (the stamp rule is a binary search per chunk scope of a born entity per tick): no movement beyond noise.

**21. The spawner schedule is transport state and the engine performs the scheduled insert (milestone 53, planned and built 2026-10-12; amends §19 (a) and §20 (a); amends 0076 §3 for scheduled lines and 0078 A3 rule 4's ownership).** The reference game's spawner (`games/reference/README.md` "Belts", Spawner: a configured rate per lane, waiting while there is no room, an integer accumulator, never a burst) needs held credit per lane; §19 (e) forbids writing the entity per insert; and the only place the credit lived, `Schedule.acc` in the host's tracker, is derived, host-only, unreadable by the sim and lost on restore (§20 (a) re-declares from the game's entities, which cannot carry it). The three game-side options fail: a stateless feeder has no rate; a tick-derived accumulator must drop the credit on a refusal (stalls lose production, against the line) and still needs a replay flag on the wire; writing the entity at every stall edge is nearly a write per insert on a saturated belt and stores timing the scripted drivers cannot agree on. So the line record carries `sched: Option<Schedule>` (`period`, `acc`, `kinds`, `next`, `paused`) behind a presence bit of its tag (a line without one is byte-identical, as segments ride bit 7, §13), hashed with the store (0076 §7) but not in the per-chunk structure hash (§17 (b): motion, replicated by the forecast's `RunList` as A3 rule 4 says), restored with the store; `advance` runs the schedule's rule first thing (at most one `insert_back` a tick, the credit kept on a room refusal and never grown, `paused` by the item cap), the same rule the replica's follower replays, so a scheduled line cannot mismatch; `set_spawner` writes that state once (`BadPeriod` below 256; a game's `insert_back` on a scheduled line is refused: the engine owns its inserts, the game owns what and at what rate); surgery carries the schedule to the piece that holds the line's back (`join` carries the back line's schedule to the merged line, `split` moves it to the back piece, `destroy` drops it; a `join` is refused when both lines are scheduled and when only the front one is, since the merged line's back would be the back line's and the spawner would sit mid-line: a spawner tile accepts no input from behind, the game's rule). `declare_spawners` stays for games that insert themselves. As built (milestone 53): the schedule rides bit 6 of the line's out tag as 13 bytes; the line record grows 88 → 104 B and a host keeps an id-sorted list of scheduled slots (half the line cap, 4 B each) so `advance` visits only scheduled lines (one spawner among 1,000 lines visits one slot a tick); `set_spawner` is `Full` past the tracker's room (half the line cap, shared with `declare_spawner`), `BadPeriod` below 256, `BadItem` for item 0, and a game's `insert_back` on a scheduled line is `Scheduled`; a restore keeps the decoded schedules armed and the tracker's close skips them (a game-declared rule beside stored schedules restores with 0 mismatches); the arena at the recommended caps is 21,757,984 B for a host and 18,022,416 B for a replica (amending §17's 16,646,160 and 0078 A8's 21,168,160 / 17,498,128), the phone pair of 12,288 lines / 98,304 items 8,200,224 B (188,384 B under 8 MiB) and 6,799,376 B. `fx-belts`' spawners set their schedule once and write nothing: 13 of its 14 goldens moved (the entities unwritten, 13 B per scheduled line; items and sink counts identical every tick), the bench world's frames fell from 53,501 to 107 B a tick in the native bench (111 B in the Node `.wasm` run of `tick-belts-large node`, which pins it), and `slow_tick_belts_large` fell from 1.2638 ms to 0.2146 ms (the median of 0.2203 / 0.2125 / 0.2146 at quiet load; tick 0.236 → 0.12, frames 1.04 → 0.10): the baseline is re-recorded there with the reason, and the bench's frames phase now measures structure-only frames, so the entity-delta path it used to gate is no longer in the bench (recorded as a known gap).

**22. Undergrounds are three lines per lane, the hidden one segment-less, and pairing is derived from the layout in the tick (milestone 55, 2026-10-12).** The reference game's underground pair (`games/reference/README.md` "Belts", Undergrounds: an entrance and an exit facing the same way, up to four tiles apart, the nearest exit pairs, a new entrance between them steals) needs an item path the client never sees. The engine already has the shape: a line without segments has no geometry, so the host never routes it to a connection (`host/lines.rs` puts only lines whose anchor chunk a connection holds; a segment-less line anchors nowhere), the per-chunk hash never covers it (§17 (b): the tile index), and `draw_items` draws nothing for it; it is still sim state in the full hash (0076 §7) and saved with the store. So per lane an entrance holds a straight 128-position line from the midline back, a paired entrance owns a hidden line of `(gap + 1) x 256` positions with no segments linked `Next` from the entrance's line and `Next` into the exit's, and an exit holds a straight 128 from the front edge to the midline; an unpaired entrance dead-ends at the hood, an unpaired exit's back is a dead end for the belt behind it. No engine change. Items surface at the exit as `Arrival`s (0078 A14: 10 B each, 148 B/s per saturated pair). **Pairing is never stored**: it is recomputed in the topology's tick from the layout alone (the first underground on the entrance's axis within five tiles decides: an exit facing the same way pairs, anything else unpairs; perpendicular undergrounds are passed over), reconciled for every entrance whose five-tile ray touches an edited tile, writing only differences; a steal or a changed gap destroys and re-creates the hidden lines with their items (question 14 (c)'s default: a broken pair destroys the hidden items), as a rotation turns one end only and unpairs it (question 14 (a), the README's assumed line; Factorio turns both) and perpendicular undergrounds are transparent (14 (b)). Rejected: a stored partner id on the entity (a second source of truth for what the layout already says; every edit near a pair would have to repair it), an engine "hidden geometry" line kind (the segment-less line already has every property wanted; kept as the fallback if a game needs the hidden stretch drawn), and classifying an underground half by entity kind in `mapped` (it is a pure `TransportRead` read with no world; a straight 128 segment on a tile that holds exactly two lines is an underground end, four lines a splitter half). Capacity per lane at gap 4 is 24 (2 + 20 + 2; the wiki's 44 counts both lanes of the entrance entity). The full-game golden gains an underground passage (first changed checkpoint 1150).

**23. The scenarios' measurements (milestone 56, 2026-10-12; amends §11 and §16 with figures, records question 11 on a balancer).** The reference game's layouts are built from a text map (one parser in the Rust tests and one in TypeScript, both pinned by one hash per layout) and run natively, in the netcode harness and in the browser with conservation exact (made = live + sunk + destroyed; the topology counts the items it destroys behind `debug_assertions`). What the measurements decided: (a) **§11's spread is real and bounded**: a saturated ring through a splitter (a `Fork` link in the cycle, so the cut leader's dry pass does not apply) carries 273 crossings a lane per 1,000 ticks at its cut against 374 on a plain fed ring: 0.273 a tick = 24 / 88, exactly a packed block spreading to `SPACING + speed`; a plain ring of belts and curves is a simple `Next` cycle and rotates rigidly (every item moves exactly 24 a tick; the lane's lap is its length / 24). The dry pass stays as built: a loop through a splitter is the overflow idiom and loses 27 % of a saturated lane's throughput only while packed and moving; milestone 56b (extending the dry pass to `Fork` and `Merge` cycles) is left conditional on a game that needs it. (b) **§16's cursor is not needed**: eight blocked side-loads on a packed 96-item lane cost 0.7 µs a tick in the whole host tick against 0.2 µs without them (test build; ceiling 50 µs pinned by `slow_sideload_chain_cost`); the walk a blocked side-load makes over its target is cheap at reference scale and the cursor is not built. (c) **Question 11 on four inputs**: a 4x4 balancer (two splitter stages, one underground crossing) with every input saturated sinks 187 or 188 items a lane in 500 ticks on every output (first sinks 75-84 ticks after configuration), but with one output blocked the steady window carries stone 374, iron 374, wood 376 and coal 0: the blocked stage's left input wins its one open output and backs the other up, then the first stage's left input wins again, so one input starves through two splitters by update order. With one input alone (coal at saturation) its 374 items leave by all four outputs, 47 / 46 / 47 / 47 a lane; with all four inputs at 0.2 a tick every output lane sinks exactly 100 but each input reaches only two outputs, half each (the fork toggles lock to the inputs' interleaving at equal rates): the balancer balances throughput, not each input's spread. Recorded for Tyler with the figures; an engine input turn is the fix if he wants Factorio's fairness across inputs. (d) **The balancer's forecast cost**: 1,392.5 B/s of sections 12 and 13 over 20 s of steady flow, all `Arrival`s (3,000 at 9.3 B with framing, 0 States, 0 lists), 8.5 % of 0078 A5's 16,384 (0078 A15). (e) **Mixed speeds** (fixture only, the reference game has one speed): four `Next`-linked chains at 24, 72, 96, 24 hold spacing across every speed change and sink at the slowest line's rate (the `mixed-speeds` golden), and the junctions cost 0.91 lists and 0.34 arrivals a tick (0078 A8's figures pinned). A restore mid-flow continues exactly: the reference tests replay the saved world with its caps through `engine::testing::replay` and the restored world's hash 200 ticks on equals an uninterrupted twin's.

## Alternatives rejected

- **Hash the transport section always and regenerate every golden.** Honest but blind: a regenerated hash cannot show whether the sim behaviour of a non-belt world changed; the conditional hash keeps every existing golden as that proof.
- **Encode the free gap and skip decode validation.** A codec check that cannot fail is the defect 0069 §1 names.
- **Leave the fallback-to-genesis-replay for old saves.** A loss presented as a recovery.
- **Reserve the arena in `Store::new`.** Its signature has 18 callers and a replica would pay 7 MiB for nothing.
- **Refuse a merge landing onto a not-yet-advanced line** (§16). Deadlocks a loop whose side-load is the cut link.
- **A toggle byte on every line** (§15). Would have changed every existing record.
- **Push a rescaled squashed pair apart to `SPACING`** (§12). Fails the measured curve case and moves items an edit must not move.
- **A segment count on every line's record** (§13). Would have changed every belt golden for lines that have no segments.
- **Clamp a too-far landing to 0** instead of refusing the layout (§8). A clamp hides a lost tick of travel; refusing at `set_out` names the layout that cannot work.
- **Let items crossing a cycle's cut move twice** (§11). A visible jump once per lap at one tile, for a layout (a belt loop) players build on purpose.
- **Structures inside the chunk snapshot entry** (§17). A count byte would have moved the snapshot golden and every exact byte row; the same frame's section 12 carries them at no extra message.
- **All-or-nothing structure puts** (§17). Stalls a connection whose due puts exceed one frame.
- **`Gone` for every held line after a lost frame** (§18). O(held) and never converging on a narrow connection; the lines the lost frame changed or named, plus one level of targets, suffice once the client steps a skipped tick before the next frame's sections (0078 A8).
- **Catching the follower up after a frame's puts** (§18). Loses every crosser of a quiet tick before a structure change; the harness that stepped on its own clock hid it, so the arbiter now calls the client's own catch-up.
- **Count a run list's bytes exactly when pricing** (§18). 18 % of the bench's samples; a bound never below the written bytes costs O(segments).
- **Shrink the node to 12 B** to meet the nominal 4 MiB. Not now: positions need `u32` gaps and links need `u32` indices; the phone measurement of milestone 57 decides whether the caps or the node change.
