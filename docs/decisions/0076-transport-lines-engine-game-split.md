# 0076: Transport lines: what the engine owns and what a belt game owns

Status: Accepted (2026-10-11). Amended by [0079](0079-transport-core-decisions.md) §1 (the hash covers the store once it has held a line), §5 (the arena's size and reservation). Amends [0003](0003-game-facing-api.md) (`WorldRead`/`WorldWrite` gain a transport accessor), [0007](0007-world-model.md) §8 (two new state-budget counts) and [0011](0011-wire-format-and-deltas.md) "Deltas are the only write path" (one engine-owned exception, §7). Settles the item deferred in [0001](0001-camera-and-presence.md) Consequences and [0003](0003-game-facing-api.md) Consequences ("no sim-owned moving entity"). Implemented by the belts plan (`PLAN.md`, milestones 40 onward); the representation of items is [0077](0077-transport-item-representation.md) and their replication is [0078](0078-transport-forecast-replication.md).

## Context

Tyler wants Factorio-style belts in the reference game (requirements: `games/reference/README.md` "Belts"): two lanes per belt, straight and curved belts, side-loading, splitters, undergrounds, spawner and despawner belts; compute-efficient above all, at a stated scale (50,000 belt tiles and 250,000 items in one world tick in at most 5 ms on desktop); inserters later, adding and removing items in the middle of a belt. The engine/game rule of `docs/architecture/README.md` is "the game defines what, the engine handles when and where": the engine should hold as little as possible while leaving the game free to decide speeds, item kinds, layouts and rules.

The forces:

- Every entity today is plain data replicated whole-value and scoped to its footprint chunk ([0007](0007-world-model.md) §5, [0011](0011-wire-format-and-deltas.md)); "games must never replicate per-tick progress" (`docs/architecture/sync-and-netcode.md`). A belt line's items move every tick and a line spans chunks. Neither fits an entity.
- The client runs no tick rules ([0012](0012-prediction-and-reconciliation.md)), and Tyler holds that for belts (2026-10-11): the client follows what the host tells it.
- The prior project at `/Users/tyler/repos/belts` reverse-engineered Factorio's model (its `docs/dev/sim.md`, `docs/12-belt-physics-measurements.md`): fixed-point positions of 1/256 tile, a minimum spacing of 64 positions, per-tile "transport lines" chained front to back, side-load entry points, per-lane splitter toggles. Its code is TypeScript and not transferable; its measured rules are the reference. Factorio is the inspiration, not the target: a simpler rule set is expected and every simplification is recorded in the game's requirements.
- The engine ticks at 20 Hz ([0006](0006-time-units.md)), not Factorio's 60, so an item moves 24 positions per tick at the reference speed (3/8 of a spacing) and faster lines move more than one spacing per tick.
- Zero allocation per tick ([hot-paths](../../.claude/rules/hot-paths.md)), determinism ([determinism](../../.claude/rules/determinism.md)) and the fast-tier test budgets apply unchanged.

## Decision

**1. The engine owns one generic transport-line module, `engine::transport`, as sim state.** It lives in `Store<G>` beside entities and timers, is encoded, hashed and snapshotted with them, and is the same type on the host and in the client replica. It knows lines, lanes-as-lines, items as opaque ids, runs, spacing, speeds, hand-offs, and nothing about belts, tiles, tiers or what an item is. Its vocabulary:

- `LineId(u32)`: host-allocated, monotonic, never reused (the `EntityId` policy of [0022](0022-entity-ids-and-provisional-ids.md) §1 applies; `0` is none). A line is one lane: a belt tile contributes two lines, one per lane, or extends two existing lines.
- A line has `len` (positions, 1/256 tile, `u32`), `speed` (positions per tick, `u16`, set by the game, `1 <= speed < len`), an `Output`, and its items front to back ([0077](0077-transport-item-representation.md)). Position 0 is the front (exit); positions grow toward the back; items move toward 0; the occupiable domain is `[0, len - 1]`.
- `SPACING = 64` positions is an engine constant: the minimum distance between two items on one line and across a plain hand-off (4 items per tile per lane). A game cannot change it; the run representation of 0077 relies on it.
- `Item(u16)`: opaque to the engine; `0` is reserved for "none". The game maps its item ids onto it.
- `Output::{DeadEnd, Next(LineId), Merge { line, at }, Fork { a, b }, Sink}`: what the front of a line feeds. `Next` is a plain hand-off (lane preserved, position continues: landing `target.len - overshoot`). `Merge` is a side-load: the item lands on `line` at position `at - overshoot` if there is room (`SPACING` clear on both sides), else waits at the feeder's front. `Fork` alternates items between `a` and `b` per line with a one-bit toggle that flips only when the item is delivered to the preferred side; a blocked side sends the item to the other; both blocked, it waits. `Sink` deletes the item and counts it. Undergrounds need nothing here: a hidden stretch is just a longer line.
- Big steps: the engine handles `speed >= SPACING` (several items crossing a line front in one tick) in every output kind, processing front to back. `speed < len` for every line keeps each item to at most one hand-off per tick; `set_speed` and `create` refuse otherwise.

**2. The engine owns the per-tick rule.** `Transport::advance` runs inside `Sim::step` after `G::tick` (so the game's inserts of that tick are visible to the advance), over every line in update order: reverse topological (a line after the lines it feeds, so a hand-off lands on a line that has already moved; a cycle is cut at its lowest `LineId`; order is recomputed only when the graph changes). The squash rule of the prior project's measurements (`docs/12-belt-physics-measurements.md` §3c) holds: a blocked item advances by `min(speed, gap_after_leader_move - SPACING)`.

**3. The engine owns line surgery and item primitives; the game owns topology rules.** The API (host tick only, §6): `create(len, speed) -> LineId`, `destroy(line) -> items`, `extend_back`/`extend_front(line, by)`, `shrink_*`, `split(line, at) -> LineId`, `join(front, back)`, `set_out`, `set_speed`, `rescale(line, new_len)` (positions scaled by `new / old`, rounding down, for a reshape); `insert_back(line, item) -> Result<(), Full | NoRoom>` (lands at `max(len - speed, tail + SPACING)`; a spawner's primitive), `insert_at(line, pos, item)` and `remove_at(line, pos) -> Option<Item>` (an inserter's primitives: `SPACING` clear on both sides to insert; the nearest item within half a spacing to remove), `front(line) -> Option<(Item, pos)>`, `count(line)`. The game decides *when* to call these: which belt feeds which, shapes, curves, side-load entry positions, splitter wiring, underground pairing, spawner rates and despawner sinks are the game's tick rules, written against this API. The engine never consults a tile.

**4. Geometry is registered, not inferred.** For rendering and scope the engine needs where a line is. The game registers each line's path as a list of segments `(len, Geometry)`, `Geometry::{Straight { from: WorldPos, to: WorldPos }, Arc { centre: WorldPos, radius_q8, start_turn, sweep }}` (Q24.8 like `WorldPos`), kept in the line's structure and replicated with it ([0078](0078-transport-forecast-replication.md) §1). From the segments the engine derives (never encodes) each line's chunk set and anchor chunk (the chunk of its front point) and a tile index `tile -> [(LineId, offset)]` the game reads back (`WorldRead::transport().lines_at(tile)`); the game stores no line id in a belt entity, so a line extension never rewrites entities. A straight run of belt tiles is one segment; curves are one arc segment per lane.

**5. Rendering: the engine emits items, the game draws belts.** `transport::draw_items(view, style, out)` walks the lines whose chunk set meets `FrameView::visible()`, evaluates every item's position at the frame's render time along the forecast ([0078](0078-transport-forecast-replication.md) §2), maps it through the segments to a `WorldPos`, and appends one `DrawList::sprite` per item with `style(item) -> (SpriteId, layer, size, colour)` supplied by the game. A `min_px_per_tile` in the style skips items when they would be smaller than a few pixels (the game's LOD, [0018](0018-renderer.md) §6). Belt tiles themselves are game sprites from the game's own `extract`.

**6. Topology changes are host tick rules, never `apply` writes.** `WorldWrite::transport_mut()` is `Ok` only inside `TickCx` (and `genesis`/`migrate`); under `Predicting` and in `apply` on the host it is `Err(Unknown)`, so `?` makes an action that touches it `NotPredictable` on the client and a bug on the host (a debug assertion). A belt placement is therefore predicted the way a furnace is: `apply` validates and spawns the belt entity; the entity's auto-wake (`next_woken`, [0046](0046-genesis-writes-unlogged-and-timers.md)) lets the game's `tick` map it onto lines on the host in the same tick it is applied. A predicted belt renders as a `PREDICTED` entity with no items until the host's line structure arrives. A predicted placement is a hint and cannot fight a forecast ([prediction rule](../../.claude/rules/prediction.md)). Rotation and pick-up follow the same shape: the entity put or despawn is predicted; the line change is the host's.

**7. The transport store is the one part of `Store` not mutated through `Delta`.** `advance` and the surgery API mutate it directly on the host; the replica is mutated by `Transport::apply_structure` and `apply_forecast` ([0078](0078-transport-forecast-replication.md)). This is an explicit exception to [0011](0011-wire-format-and-deltas.md) "Deltas are the only write path", confined to `engine::transport`; `Store::apply(&Delta)` stays the only mutator of everything else. The full state hash and snapshots include the transport store byte for byte; the per-chunk desync hash includes only line *structures* anchored in the chunk ([0078](0078-transport-forecast-replication.md) §6).

**8. State budget.** Two counts join [0007](0007-world-model.md) §8: `max_lines` (default 32,768, nominal 64 B each) and `max_items` (default 262,144, nominal 8 B each), both world params, both deterministic counts; the arena for lines and items is reserved at world creation from them, so no per-tick allocation can occur. `create` returns `Err(Full)` at the line cap and `insert_*` returns `Err(Full)` at the item cap; tick rules are never refused by the budget check, so the game handles `Full` (a spawner waits; a belt that cannot get a line stays unmapped and the game shows it inert). On the baseline phone these defaults fit the 8 MiB slack of 0007 §8's split (2 MiB + 2 MiB); desktop and server raise them. Actions never create lines or items (§6), so `Growth` is unchanged.

**9. What the reference game owns.** Belt, spawner, despawner, splitter and underground entities (plain data: anchor, direction, kind, derived shape, spawner config), `PlaceBelt`/`RotateBelt`/`PickUpBelt` actions, placement validation by traits, the topology rules of its requirements section, one speed (24 positions per tick), the item id table, belt art and animation, the item style table, the configuration panel. The engine fixture `fx-belts` exercises every engine primitive without the reference game's rules; engine tests never use the reference game ([0020](0020-testing-strategy.md)).

## Alternatives rejected

- **Belts as a game-side system with no engine support.** Every belt game would rewrite replication, interpolation and rendering of moving items, which is exactly the engine's job ("the engine handles when and where"); and the forecast path of 0078 needs host and replica hooks a game cannot reach.
- **Belt tiles as tile-overlay bits instead of entities** (compact replication, free terrain-shader rendering). Rejected for this effort: splitters are 2x1 entities, placement and pick-up already address entities by tile, and the DrawList capacity holds a dense viewport at maximum zoom-out (about 37,000 belt sprites of 65,536). Kept as the fallback if the dense-viewport frame budget is missed (milestone 50): a derived `aux` bit per belt tile plus an animated tile visual.
- **Items as entities.** 250,000 whole-value puts per hand-off burst and per-tick progress on the wire; the model this ADR exists to avoid.
- **Per-tile lines, never merged** (the prior project's D4). Correct and simple, but per-tick cost is O(tiles) even when nothing changes; the 5 ms budget at 50,000 tiles needs O(lines that changed). Merging is the game's call per hand-off (it may keep per-tile lines where it wants), the engine only provides `join`/`split`.
- **Topology in `apply`, predicted.** A predicted `join` or `split` on a partial replica would create provisional line ids and fight the host's forecast for the same line; §6 keeps every line write authoritative.
- **A per-game `Transport` trait with game-written advance rules.** Two implementations of the squash and hand-off rules (host and tests) would drift, and the engine's forecast tracker (0078 §3) has to see every hand-off decision, which only works when the engine makes them.
- **Spacing as a per-line parameter.** Nothing asked for it; a run representation keyed on one spacing is simpler and faster (0077).

## Consequences

- `Store`'s encoding changes (a transport section), so the snapshot format version in `persist/identity.rs` bumps and existing saves of the reference game load as `SaveIncompatible`; accepted for a game with no live players (milestone 42 records the bump; Tyler is told in that milestone's report).
- `WorldRead`/`WorldWrite` gain `transport()`/`transport_mut()`; `View` and `FrameView` expose the replica's transport read side; `Predicting` returns `Unknown` for writes.
- New engine budgets: the tick at the stated scale (`tick.beltsLargeMs`, milestone 45), bytes per second for a saturated viewport (0078 §5), items in view under the frame budgets (milestone 50). Each is a `budgets.json` row with a benchmark that can trip ([0069](0069-working-rules-learned-in-phase-3.md) §B).
- Deferred to the plan's measurements: whether lines need position-window culling per subscription (0078 §4), the dense-viewport fallback (above), `max_lines`/`max_items` defaults on the phones (milestone 57).
- Trigger to revisit §1's `Output` set: a game needing a filter, priority or a third output writes an ADR; the fork's toggle rule is the one Tyler chose (50/50, no priority or filter).
